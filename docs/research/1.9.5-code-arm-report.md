# 1.9.5 The Code Mode arm of the eval

Date: 2026-11-23. Compares with the baseline in `0.2.5-baseline-report.md`. Targets are
those set in `docs/decisions/0.2.6-success-targets.md`.

## Result

Final run (run 3), 30 tasks, five runs each, per model. "Direct" is the baseline arm:
every tool definition offered, each tool called directly.

| | Claude Haiku 5.5 | GPT-6 Luna | Target |
|---|---|---|---|
| Input tokens, bounded tool-heavy tasks | 62% lower (39,246 to 15,032) | 39% lower (24,013 to 14,638) | At least 30% lower, each model: **met** |
| Input tokens, exploratory tasks | 19% lower | 11% lower | No target |
| Correct, all tasks | 145 of 150 (direct: 149) | 150 of 150 (direct: 149) | |
| Success difference, all tasks | -2.7 points (95% interval -6.9 to +0.9) | +0.7 points (-1.9 to +3.7) | No more than 5 points below: **met**, though Claude's interval reaches past 5 |
| A task that passes direct and fails every run here | **`rollback-command`: 0 of 5 (direct: 4 of 5)** | None | None allowed: **not met on Claude** |
| Model turns per task | 3.9 (direct: 2.1) | 4.5 (direct: 2.3) | Reported only |
| Scripts that failed | 19 of 433 (4.4%) | 0 of 530 | 10% per model, set by the project owner on these numbers: met |
| Median time per task | 4.3 s (direct: 3.0 s) | 6.2 s (direct: 3.8 s) | Not the latency budget, which covers what the core adds |

Intervals are Newcombe's, from two Wilson intervals.

**The saving comes from the big tasks.** Where a direct run pulls tens of thousands of
tokens of tool results into the conversation, a script returns a count. On small tasks
Code Mode costs more input tokens than direct calls: 5 of 30 tasks on Claude, 14 of 30
on GPT, by 1% to 67%. The extra turns to find and learn a tool outweigh a result that
was small anyway.

**The one failing task** asks how to roll back a deploy. The answer is in a file in the
repository. Offered every tool with its description, Claude reads the file. Offered tool
names only, it lists them, sees nothing about deploys, and answers that it cannot tell,
without calling a tool. GPT reads the file. This goes to task 1.9.6.

## Three runs, and what changed between them

| Run | Change | Claude: correct, tool-heavy saving | GPT: correct, tool-heavy saving |
|---|---|---|---|
| 1 | As built | 145, 61% | 150, 25% |
| 2 | `search()` ranks by matching words | 138, 66% | 150, 40% |
| 3 | The description says to search by what a tool does, and that `search('')` lists every name | 145, 62% | 150, 39% |

- **Run 1 found a product fault.** `search()` required every word of the query to be in
  a tool's name. Models ask in phrases, so most first searches returned nothing and two
  or three turns went on guessing words. GPT missed the 30% target because of it.
- **Run 2 fixed that and exposed another.** With plausible results for any query,
  Claude stopped listing all tools, searched for the subject of the task rather than for
  a capability, and gave up when nothing fitted. Its success fell 7.3 points.
- **Run 3** changed the wording only.

## Limits

- **The wording was tuned on the tasks it is measured on.** Three runs, two changes,
  the same 30 tasks. The final numbers flatter it. A fair test needs tasks the wording
  has not seen.
- **One upstream, fifteen read-only tools, invented data.** A larger catalog changes
  what search returns and what `search('')` costs.
- **Cost is not compared.** The baseline went through OpenRouter and this arm through
  each provider's own API, which bill cached input differently. Token counts were
  checked to agree across the two routes: nine tasks per model rerun direct, all within
  0.4%.
- **150 runs per model** detects a success drop of about 5 points, not a smaller one.
- **Small, cheap models only.** Larger models were not run.
- Scripts ran on the deployed test Worker, in the real sandbox, through the real broker
  and static check. The audit log and policy store were in memory.
