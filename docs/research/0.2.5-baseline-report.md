# 0.2.5 Baseline report: direct calls and tool search

Date: 2026-11-22. Status: done. This is the Phase 0 baseline the PRD asks for: how the
target models do on the task suite before any code tool exists.

## Summary

- Both models answer almost everything correctly with direct tool calls: 149 of 150 runs
  each (99.3%).
- Tool search (offering tool definitions only on request) cut input tokens by 10% on
  Claude Haiku 5.5 and 13% on GPT-6 Luna. It cost one extra turn per run.
- Tool search left GPT-6 Luna's success unchanged. On Claude Haiku 5.5 success fell from
  99.3% to 95.3%. That 4-point fall is below what this suite can detect in general (5
  points), but it is not spread evenly: five of the seven failures are one task that
  Claude failed every time under tool search and once in five without it.
- Most tokens are tool results, not tool definitions. The eight most expensive tasks, all
  of them fetch-and-count tasks, use 54% of Claude's input tokens. Deferring definitions
  cannot reduce that. A code tool can, because the script would read the pages and return
  only the count.
- The whole baseline cost $1.40 (600 runs).

## What was run

| | |
|---|---|
| Tasks | 30: 20 bounded tool-heavy, 10 exploratory (`src/eval/tasks/github-tasks.ts`) |
| Tools | 15 read-only GitHub tools on invented, fixed data (`src/eval/fixtures/`) |
| Models | Claude Haiku 5.5, GPT-6 Luna, each at its default reasoning effort |
| Arms | direct (all 15 tools offered); tool search (`search_tools` and `call_tool` only) |
| Runs | 5 per task per model per arm: 600 in total, 150 per model and arm |
| Route | OpenRouter, pinned to each model's own provider. No run needed the fallback route. |
| Metering | Tokens as each provider reported them, per turn, summed per run |
| Raw results | `docs/research/data/0.2.5-baseline.jsonl`, one line per run |

Command: `npx tsx scripts/eval-suite.ts --arm direct --arm tool_search --runs 5 --cap 5`.
The tables below are printed by `npx tsx scripts/baseline-report.ts <file>`.

## The smallest drop this suite can detect

With 150 runs per model and arm and a direct-arm success of 99.3%, a second arm has to be
about **5 percentage points** worse before the difference shows reliably (one-sided test
at 5%, 80% power). Two cautions:

- The calculation treats runs as independent. Five runs of the same task are not, as the
  `rollback-command` result shows, so the true figure is somewhat larger.
- With success this near 100%, the suite can show a drop but cannot show an improvement.

This is the number task 0.2.6 needs when it sets the drop that counts as significant at
Gate 1. Halving it would take about four times the runs.

## What the failures were

- **`rollback-command` under tool search (Claude, 5 of 5).** The answer is in a file,
  `docs/deploy.md`. With all tools on offer, Claude reads the repository and finds it.
  Under tool search it searched for tools about deploying or rolling back, found none, and
  answered that it had no such tool (seen in two re-runs with answers shown; the five
  baseline runs themselves did not record answers). This is a real effect of tool search
  on a weaker model: it cannot see that a general tool would do the job. GPT-6 Luna
  passed this task every time.
- **`open-issues-org` under tool search (3 runs across both models).** In a re-run with
  answers shown, Claude gave the right number, 35, followed by an explanation containing
  other numbers. The check accepts an answer only if it names no other number, as the
  prompt asks for "the number only". So some or all of these three are format failures,
  not wrong counts. This was seen once in a re-run and is inferred, not confirmed, for the
  baseline runs.
- The other two failures are single wrong answers on fetch-and-count tasks.

From now on the runner saves each final answer beside its result, so a changed check can
re-score old runs without paying for them again.

- Bounded tool-heavy tasks use about 2.4 times (Claude) to 2.8 times (GPT) the input

  commits to produce one number or one name. The model reads tens of thousands of tokens
  of GitHub fields to do a count.
- Deferring the 15 tool definitions saved 10% to 13%. Everything else is tool results and
  the conversation itself.

For task 0.2.7 this points the way the PRD expected: the code tool is worth building
first for bounded, list-heavy work, where a script could do the paging and counting and
return a short result. Nothing here measures the code tool itself; that is task 1.9.5.

## Cost, and why it is not a fair measure between arms

| Model and arm | Tokens times list price | Charged by OpenRouter |
|---|---|---|
| Claude Haiku 5.5, direct | $0.509 | $0.509 |
| Claude Haiku 5.5, tool search | $0.470 | $0.470 |
| GPT-6 Luna, direct | $0.294 | $0.139 |
| GPT-6 Luna, tool search | $0.262 | $0.285 |

For Claude the charge equals tokens times list price. For GPT-6 Luna it does not: the
direct arm was charged less than half of list and the tool-search arm slightly more than
list. That pattern is what automatic prompt caching would produce, since the direct arm
sends the same 15 definitions at the start of every request and the eval repeats each
task. I did not confirm this from the usage details. Either way, the dollar figures for
GPT reflect how this eval repeats itself, not what real use would cost, so the arms are
compared on tokens.

## Corrections made to get here

- **A flaw in the fixture, found and fixed.** The first 600 runs showed 126 tool errors,
  120 of them on one task, `commit-authors-dashboard`. The fixture listed feature branches
  but answered "404 Not Found" when asked for a branch's commits, which GitHub would not
  do. Claude tried every branch and spent nearly a fifth of its tokens there. The fixture
  now gives every listed branch a history, the task's wording now says "on the main
  branch", and that one task was run again on both models and arms (20 runs, $0.11). The
  results above use those 20 runs in place of the original 20. Tool errors fell to 6.
  Success on that task was 5 of 5 in every cell both before and after.
- **Earlier pilot figures are superseded.** The pilot in `docs/decisions/0.2.5-tool-search-arm.md`
  suggested savings of 16% and 11% from one pass; the baseline says 10% and 13%.

## Limits

- Two cheap models, one effort setting, 30 tasks on 15 tools, invented data. Larger
  models, more tools or real repositories could change every number here. With many more
  tools, definitions would be a larger share and tool search would save more.
- The tool-search arm is this project's own portable design (two fixed tools). A
  provider's built-in tool search may behave differently and was not measured.
- Five runs per task is enough to see a task that always fails, not to rank tasks.
- The fixture's responses are shaped like GitHub's from knowledge of its API, not copied
  from live responses, so token counts are close to real ones, not equal.

## Spend

The baseline cost $1.40 as reported here, $1.71 including the 20 superseded runs and the
re-run. All eval work on 2026-11-22 came to about $2.93.
