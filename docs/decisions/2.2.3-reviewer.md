## What the reviewer is

Code can check that a reply is well formed, small enough and free of secrets. It cannot
tell whether the reply is what was asked for. When a call to the `code` tool comes with
acceptance criteria, a model from a different family from the one doing the work reads
four things and nothing else: the request, the criteria, the output and the run report.
It answers one question: does the output meet the criteria?

## What it can and cannot do, fixed in code

- **It can pass or block. It cannot edit.** Nothing it writes is handed on. Only its
  verdict and the numbers of the criteria it found unmet are used.
- **A pass** marks the run report `verification: "passed"`.
- **A block** withholds the result. The model gets a new error code, `review_blocked`
  (contract 1.8.0), saying which criteria by number, and may fix its script and try
  again within the retry limit. The reviewer's own words are never passed on: they
  could carry planted text back to the working model.
- **It cannot overrule a fixed check.** If the release gate failed, the reviewer is not
  asked.
- **It cannot approve a tier-2 action.** Its pass there means only "no objection"; the
  answer is "a person is still needed", never "passed". (No tier-2 action exists yet.)
- **It adds no security power.** Anything short of a clear verdict leaves the result
  released and marked `unreviewed`, exactly as if there were no reviewer: no criteria,
  no key, a spent budget, data above what the provider may receive, a provider that is
  down, or an answer that is not a verdict.
- **A result withheld for its data class is not sent to it.**

## Against text aimed at the reviewer

- The material is sent as data inside a marked block, with every angle bracket
  escaped, so text in the output cannot close the block.
- The instructions say the material may claim to be verified or tell the reviewer how
  to answer, and that none of it is to be followed.
- Only an answer of exactly the asked shape counts as a verdict:
  `{"verdict":"pass","unmet":[]}` or `{"verdict":"block","unmet":[2,3]}`. Words around
  it, extra fields, a pass that lists unmet criteria, a criterion number that does not
  exist: none is a verdict, and none is a pass.
- The two reviewer cases in the adversarial suite are now probed and defended. They
  are tested with the worst case: a reviewer model that answers "pass" to everything.
  The failed fixed check still stands, and the tier-2 action is still not approved.

What this does not stop: planted text that persuades the model to pass a tier-0 result
that does not meet its criteria. That result is then marked `passed` when it should
have been blocked. It is the same result a missing reviewer would have released as
`unreviewed`; the harm is a wrong label, not a new release. How often a small model is
persuaded is not measured.

## When it runs, and what it costs

- Only for a completed run that passed the release gate and whose call gave criteria.
  Through the MCP adapter the criteria are the calling model's own words, and most
  calls give none. A run without criteria is not reviewed and costs nothing.
- One model call a review, on verification's own key, host list and budget ($1 a day,
  $10 a month). Each call writes a usage line of its own to the platform log,
  `execward_verification`, apart from the token meter's line.
- It adds the model's answer time to the run. Not measured yet. A request is given up
  after 20 seconds, and the result is then `unreviewed`.

## Not done, or not seen

- **No call to the real provider has been made.** Every test uses a fake. The key does
  not exist yet. Until it does, every review is refused before anything is sent and
  results stay `unreviewed`, as before this task.
- **Whether `gpt-6-luna` judges well is unknown.** A first live check, within the
  $0.25, is to show that it passes a good answer, blocks a planted wrong one, ignores
  text that tries to instruct it, and answers in the asked shape.
- **Whether the request and reply shapes are right for this model** is unknown until
  that check. They follow the shapes the eval's OpenAI client uses.
- **The reviewer sees the criteria as the calling model wrote them.** A model that
  writes weak criteria gets a weak review. Criteria from the user's own request arrive
  only through the in-app adapter.
- **The cross-check's figures are not sent to the reviewer.** FR-48 also names
  critical figures; task 2.2.2 checks those by recomputation instead.
