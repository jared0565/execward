# 1.6.1 to 1.6.5 The owner's switches and who may throw them

Date: 2026-11-23. Requirements: FR-16, FR-17, FR-27, FR-49, FR-52. Status: **built and
tested. The switches are stored in the database, and the console page and its sign-in
are built (see 1.6.1-console-sign-in.md). Sign-in was switched on, and the owner signed
in, on 2026-11-24.** All of 1.6.1 to 1.6.5 are done.

## The switches

One small record, the control state, holds:

| Switch | Starts | Effect |
|---|---|---|
| Code Mode | Off | Off: no run starts. The test app offers the wrapped tools directly instead |
| Kill switch | Not set | Set: nothing runs, whatever else is on. The test app stops asking the model |
| Paused projects | None | A paused project's runs are refused; other projects carry on |
| Blocked tools | None | A run that calls a blocked tool ends |
| Onboarding | Not done | Code Mode cannot be switched on until it is |

**The state is read before every run, and within a run at most a quarter of a second
before any call a script makes** (the owner's choice on 2026-11-23, see
1.9.4-latency.md). So a switch thrown mid-run ends the script within a quarter of a
second of its next call (FR-17). The reply says which
side-effecting calls had already been made; today that is always none, because only
read-only tools exist. The script's own result is not handed over.

**No model is in the kill switch's path.** It is a field the owner sets and the broker
reads.

**Everything fails closed.** If the state cannot be read, nothing runs.

## Who may change them

Every console action takes a principal: who is asking, as established by sign-in. An
action is refused unless the principal is the owner, with two-factor sign-in completed
in the last 12 hours. A credential held by a model or its client is a different kind of
principal and is always refused.

Every change gets the next version number and an audit log entry holding who made it,
why, and the state before and after. A change that changes nothing makes neither.

Anything that lifts a protection needs a written reason: clearing the kill switch,
resuming a project, unblocking a tool. Setting the kill switch never waits for one.

## Onboarding

Records the governance profile, approvers, approved providers, project data classes,
meter level and outbound allowlist. Every field has a safe default except the profile,
which must be chosen: lightweight and formal run the same security controls, so neither
is "safer", and guessing would record a choice nobody made.

## Choices

- **A paused project and the kill switch report `code_mode_off`,** not a security code.
  A security code would escalate again every time a paused project was tried.
- **The kill switch still works when the audit log is down.** The change is made and
  the caller is told the log entry is missing. A stop control that depends on the log
  is not a stop control.
- **Two changes at once cannot overwrite each other.** Each write names the version it
  read; a stale write is retried against the new state.

## Limits

- **Sign-in is Cloudflare Access, switched on since 2026-11-24.** See
  1.6.1-console-sign-in.md for what it checks and what it cannot.
- **A script between calls is not interrupted.** A switch takes effect at the script's
  next call, or when its time limit ends it. A script that only computes runs to its
  limit, with no way to reach anything.
- **Onboarding records settings but nothing reads most of them yet.** Project data
  classes, approved providers and the meter level are still passed in by whatever builds
  the service.
- **With Code Mode off, direct calls are not governed** by the broker (see 1.9.2).
- **Reading the state** costs a database read, at most once a quarter of a second
  within a run (measured in 1.9.4-latency.md).
