# 1.3.3 Checking a call's arguments

Date: 2026-11-23. Requirement: FR-34. Threat-table row 2. Status: **done, tested in
memory and in the local Workers runtime.** No real tool was wrapped when this was
written; fifteen GitHub tools are now (task 1.5.1).

## What it does

Before the broker forwards a script's call, it checks the arguments:

1. **Against the tool's input schema** (`src/broker/json-schema.ts`): types, required
   fields, allowed values, sizes, patterns.
2. **Against the allowlists** (`src/broker/allowlists.ts`): any argument the schema marks
   as a URL must name an allowed host; any marked as a path must sit under an allowed
   folder.

| Problem | Error | Effect |
|---|---|---|
| Wrong type, missing field, unknown field, value out of range | `schema_invalid` | The script may catch it, fix its arguments and try again |
| URL or path off the allowlist | `policy_denied` | The run ends |
| The tool has no definition | `policy_denied` | The run ends |
| The schema uses a rule the checker cannot enforce | `schema_invalid` on every call | The tool is unusable until the schema or the checker is changed |

## Choices

- **A purpose-built checker, not a library.** The usual JSON Schema validators turn a
  schema into code, which the Workers runtime refuses. This one reads the schema each
  time. It covers the rules tool schemas commonly use; it is about 200 lines.
- **Unknown fields are refused by default.** Standard JSON Schema allows any extra field
  unless the schema forbids it. Here it is the other way round: a field must be listed, or
  the schema must say `additionalProperties: true`.
- **An unsupported rule disables the tool; it is never skipped.** `$ref`, `not`, `allOf`,
  `oneOf`, `patternProperties` and unknown formats are not implemented. A skipped rule
  would be a rule that silently does not hold.
- **A mistake and an attack are different errors.** A wrong type is an ordinary mistake a
  model makes and can fix. Reaching for `docs/../.env` or an unlisted host is not, so it
  ends the run and is recorded as a refusal.
- **Empty allowlists allow nothing.** A tool with a URL or path argument and no list
  cannot be called at all until the owner adds entries.
- **Ambiguous text is refused, not interpreted.** URLs must be https, with no user name
  or password, on the listed port. Paths must be plain and relative: no `..`, no
  back-slashes, no encoded dots or slashes, no control characters.
- **Errors name the field and the rule, never the value.** A value may be a secret.
- **Contract version 1.3.0.** A policy record may carry `pathAllowlist`. Optional; absent
  means no path is allowed. URL hosts use the existing `destinationAllowlist`.

## Evidence

- 69 tests: schema rules, the strict defaults, unusable schemas, 15 URL tricks, 16 path
  tricks, and the broker's handling of each outcome.
- 2 tests of the whole stack in the local Workers runtime: a script that catches a schema
  error and retries succeeds; a script that reaches for `docs/../.env` gets
  `policy_denied` with no upstream call.

## Limits

- **Only arguments the schema marks are checked against the allowlists.** A URL or path
  in a plain string field is not recognised. Each tool's schema must mark them
  (`format: "uri"`, `format: "path"`); that is part of approving a tool (task 1.5.4).
  `path` is ExecWard's own format name, not a standard one.
- **A URL's host name is checked, not where it resolves.** A listed host that points at an
  internal address is not caught here.
- **Definitions are pinned by hash in the registry** (`src/registry/`, task 1.5.4, built
  since). The broker is still handed the definition by its caller; a changed definition
  ends the run with `definition_changed`.
- **Patterns come from the tool's schema.** A badly written pattern could be slow on long
  input; input over 10,000 characters is refused rather than tested.
- **The data-flow rule for outbound tools is separate** (task 1.3.5).
