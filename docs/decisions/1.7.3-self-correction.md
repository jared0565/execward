# 1.7.3 Self-correction: retries, and none for security failures

Date: 2026-11-23. Requirement: FR-41. Status: **done and tested in memory.**

## The rule

When a run fails for a reason the model can fix, the error goes back to the model and it
may try again. Counted per task:

| What happened | What follows |
|---|---|
| A fixable failure: script error, failed assertion, timeout, bad arguments, upstream error, result too large | The model may retry. The report's `retries` shows how many failed runs came before |
| A third failure in a row | The task is closed and escalated. Any further run is refused without running |
| A success | The count starts again |
| A security failure: policy denial, static check, changed definition, quota, circuit breaker, injection signal | The task is closed and escalated at once. No retry |
| A failure a retry cannot fix: sandbox fault, Code Mode off | The task is closed and escalated |

## A reading that needs the owner's eye

The PRD says "up to two attempts (proposed)". The task says "up to two retries" and "a
third attempt is refused". These fit together only one way: **the first run plus two
retries, and a third retry is refused.** That is three runs at most. It is one number,
`SELF_CORRECTION.maxRetries` in `src/limits.ts`. If the intent was two runs in total,
set it to 1.

## Choices

- **Counted per task, by a gate the adapter holds.** The in-app adapter knows where one
  user request ends and makes one gate for it. Through the MCP adapter the server cannot
  see that, so the PRD moves the per-session count to Phase 2.
- **A refused request counts as a failed attempt** when it is fixable, such as a missing
  field. Otherwise malformed requests would be free tries.
- **A refusal for a closed task keeps the code that closed it,** so the reason stays
  visible. A used-up retry limit is reported as `quota_exceeded`, which is already in
  the fixed set of codes and already marked as not retryable.
- **Refused attempts are written to the audit log** like any other refusal.
- **Escalation happens once per task,** at the failure that closes it.

## Evidence

10 tests: the retry and its count, the limit and the refusal after it, a policy denial
and a static-check refusal each closing the task at once, every error code checked
against its retryable and security marks, the count restarting after a success, a lower
limit, and separate tasks keeping separate counts.

## Limits

- **"Escalated" calls a hook and nothing more.** The queue, the notification and the
  project pause are tasks 1.6.6 and 1.6.7.
- **The gate is only as good as the adapter's idea of a task.** An adapter that makes a
  new gate for every call gives unlimited retries. The MCP adapter is in exactly that
  position until Phase 2. Per-project quotas still bound the total.
- **The count is in memory.** If the adapter restarts mid-task, the count restarts.
- **A model can alternate success and failure** without ever reaching the limit, since
  a success restarts the count. Quotas bound this too.
- **The model is not told how many retries remain** in the reply itself; the contract
  has no field for it. The adapter can ask the gate and say so.
