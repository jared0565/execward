# 1.1.6 What the deployed core can reach

Date: 2026-11-23. Requirement: FR-24. Status: **done. Bindings, environment values and secrets
are checked against the live Worker. The open network is limited to named hosts in the
core's own code, and a test enforces that.**

## What was built

`npm run check:deployed` asks Cloudflare which version of the production Worker is live,
which bindings that version has and which secrets the Worker holds, and compares them
with the allowlist in `src/worker/bindings.ts`. It reads only. It exits 1 on any
difference.

This closes the gap the configuration check left open: that check reads the file in the
repository, and cannot see a binding or a secret added in the Cloudflare dashboard.

| Reported as a problem | Why |
|---|---|
| Any binding not on the allowlist, of any kind | Includes environment values and secrets bound as values: the platform lists them as bindings |
| An allowed name of another kind, or pointed at another database or bucket | The name alone proves nothing |
| An allowed binding that is missing | The Worker is not the one described |
| Any secret not named in `ALLOWED_SECRETS` | Seven are named there (none was when this was written); any other fails |
| A compatibility date other than the pinned one | Runtime behaviour is pinned (FR-23) |

## Evidence

- 8 tests on the comparison, using what Cloudflare actually reported.
- Run against production on 2026-11-23: the live version has `BACKUPS` (R2), `DB` (D1)
  and `LOADER` (Worker Loader), no secrets, and nothing else.

## The open network

A Worker can always make outbound requests. No binding is needed, so no list of bindings
can show it cannot. Two things cover it instead.

- **One guarded way out** (`src/net/outbound.ts`). A request goes only to a host on
  `ALLOWED_OUTBOUND_HOSTS`, today `api.github.com` alone. Verification's model calls
  (task 2.2.1) go through the same guard with a list of their own, `VERIFICATION_HOSTS`
  (`api.openai.com`); neither can reach the other's hosts. HTTPS only, the standard port,
  no user name or password in the address, and no redirect is followed. A refusal does
  not repeat the address.
- **A test that reads the code** (`test/outbound.test.ts`). It follows the imports from
  `src/worker.ts`, and fails if any file the production Worker loads calls the
  platform's fetch, opens a socket, or imports a module that brings its own network
  client. It also fails if the Worker comes to load the eval harness or the test app,
  which do call model providers. The check is itself tested against planted examples.

A script in the sandbox has no network at all (tested on Cloudflare, task 1.2.8).

Evidence: 23 tests. On Cloudflare, the GitHub connector on the test Worker now goes
through the guarded fetch, and the deployed tests that read from GitHub pass.

## Limits

- **A compromised dependency is not stopped.** Code inside the Worker that calls the
  platform's fetch directly goes wherever it likes. The test reads this repository's
  files, not `node_modules`. The supply-chain controls are what stand against that.
  Cloudflare offers no per-Worker list of allowed hosts for the main Worker.
- **The production Worker's outbound requests all go through the guard:** the GitHub
  connector, the GitHub App's token exchange, the write check and verification's model
  calls. (When this was written production made none.) The test above fails if a served
  route is given anything other than `outboundFetch()` that reaches the network.
- **The test reads source text.** A call built in a way it does not look for, such as
  a name assembled at run time, would pass it.
- **Run by hand.** It needs a signed-in Wrangler, so CI cannot run it. Someone has to.
- **A moment in time.** It says what is live now. A binding added and removed between
  two runs is not seen. Cloudflare's own audit log is the record of that.
- **It trusts Cloudflare's report** of the bindings.
