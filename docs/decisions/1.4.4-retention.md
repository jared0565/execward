# 1.4.4 Retention and deletion on request

Date: 2026-11-23. Requirements: FR-21, the script-retention decision, flag 5. Status:
**done. The rules are built and tested in memory and on a local D1 database, and the
production Worker applies them once a day** (`src/worker/scheduled.ts`, since later on
2026-11-23; see docs/decisions/production-schedule.md).

## The rules

| What | Kept for | Then |
|---|---|---|
| Full text of an entry: the script, call arguments, error text | 7 days | The text is removed; the entry stays |
| The entry itself: number, time, kind, run and project names, hashes | 90 days | The entry is removed |
| Full text of every entry of a run that included a security event | 90 days | Removed with the entry |
| One project's logs, when the owner asks | Until asked | The text of every entry of that project is removed at once, and the deletion is recorded |

After each of these the chain still verifies.

## How deletion and a tamper-evident chain fit together

- **The chain covers the hash of an entry's text, not the text.** So the text can be
  removed and every hash still matches. Text that is still present is still checked.
- **Old entries are removed from the front only, oldest first.** The number and hash of
  the newest removed entry are kept as the log's new starting point. Verification starts
  from there. Without that starting point the shortened log does not verify, so a start
  cannot be invented.
- **The database enforces the same shape.** A row may be changed only by removing its
  text. A row may be deleted only if it is the oldest and more than 90 days old. Tested:
  deleting from the middle, deleting a recent row and editing a field are all refused.

## Choices

- **A security event keeps its whole run's text for 90 days,** not only its own entry.
  The script is in the run's first entry and the refusal in its last; the script is the
  evidence.
- **Deleting a project's logs removes the text, not the outline.** Each entry's number,
  time, kind and the project's name stay until they are 90 days old, because cutting
  entries out of the middle would break the chain for everyone else's entries. The text
  is where any personal data is.
- **The deletion is itself logged,** with the number of entries erased.
- **The migration file was edited rather than added to.** `0002_audit_log.sql` had been
  merged but never applied to any database. From its first real use, changes go in new
  files.
- **The 90 days is written in two places:** the limits file and the database trigger. A
  trigger cannot read the limits file. Both say so.

## Evidence

- 9 tests in memory: each period at its boundary, a run with a security event, numbering
  after everything is removed, deletion on request, tampering still detected afterwards.
- 3 tests on a local D1 database: retention end to end, deletion on request, and seven
  attempted changes of which exactly the three allowed ones succeed.

## Limits

- **The timer runs it daily.** When this was written nothing called `applyRetention`.
- **Deleting one project's records has a command** since 2026-11-27 (the owner's
  decision): `npm run project:erase -- --project NAME --yes --reason "who asked, and
  when"`. It needs a signed-in Wrangler, like the emergency stop. It removes the text
  of the project's log entries and its closed queue items, and writes one entry with
  the counts, the reason and who (`src/audit/erase.ts`). It refuses while an item of the
  project is still open in the queue, and writes nothing for a name with no records.
  Not run on production yet.
- **Closed queue items are removed 90 days after they were raised** (2026-11-27, the
  owner's decision), in the daily round. An item can hold an error's words, a run report
  and figures, and nothing removed one before. An open item is never removed.
- **While the kill switch is set, nothing is deleted** (2026-11-27, the owner's
  decision): not log text, not old counters, stats rows or queue items, not old backups.
  Each held job says so in the round's record. An incident's evidence must not age out
  while it is being looked into. The first daily round after the switch is cleared does
  what was held.
- **Removing text is allowed at any time, by design,** so someone with database access
  can wipe the text of entries without breaking the chain. The outline survives and the
  entry count does not change, but the evidence is gone. The daily backup (task 1.4.5) is
  the defence.
- **The starting point lives in the same database** as the log. Someone who can rewrite
  both can shorten the log from the front undetected. The backup covers this too.
- **A project's name stays in the outline for up to 90 days after its logs are deleted.**
  If a project name could itself identify a client, choose names that do not.
- **Backups are kept for seven days** (docs/decisions/1.4.5-backups.md), so text that
  retention or an erasure has removed lives on in a backup for up to seven days more.
- **Periods are measured from when an entry was written,** to the millisecond, not by
  calendar day.
