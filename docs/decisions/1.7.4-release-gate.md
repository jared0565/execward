# 1.7.4 The release gate

Date: 2026-11-23. Requirements: FR-47, and the "unreviewed" marking of FR-48. Status:
**done and tested in memory.** Contract version 1.5.0.

## What it does

The gate is the last step before a reply is handed over. It runs four fixed checks on
exactly what is about to be sent: the result, the captured logs and the error text.

| Check | Fails when | Reported as |
|---|---|---|
| Format | The result is not plain JSON | `sandbox_fault` |
| Size | The result is over the size limit that should already have been applied | `sandbox_fault` |
| Secret scan | The result, a log line or an error message contains something shaped like a credential | `policy_denied` |
| Data class | The run read data above the project's class and the reply was not withheld | `policy_denied` |

A failed check replaces the whole reply with an error. It is not repaired, and the gate
takes no input that could turn a fail into a pass. The failure message names the kind of
thing found and never repeats it.

## What "verification" now says

| Value | Meaning |
|---|---|
| `unreviewed` | The result passed the fixed checks and was released. No independent reviewer looked at it |
| `failed` | A fixed check withheld the reply |
| `not_applicable` | Nothing was handed over: the run failed on its own or never started |
| `passed` | Not used yet. Reserved for a result an independent reviewer has passed (Phase 2) |

Every result released today is `unreviewed`. That is deliberate: saying `passed` after
only fixed checks would claim more than was done.

## Acceptance criteria

The criteria a caller sends are recorded in the audit log before the run starts and
returned in the run report, marked `model_supplied`. Through this route they are the
model's own words, not the user's.

**Code does not judge them.** They are free text, and whether a result meets "names the
oldest issue" is not something a fixed check can decide. That is the reviewer's job
(FR-48, tasks 2.2.x). A result that plainly ignores its criteria is still released, as
`unreviewed`.

## Choices

- **A secret in the output is a security failure.** It closes the task and escalates,
  like a policy denial. A script that returns a credential has either been handed one by
  an upstream or is trying to move one.
- **The two overlapping checks are kept.** Size and data class are enforced earlier; the
  gate confirms they held. If an earlier step is ever broken by a change, the gate fails
  closed instead of leaking.
- **The gate's four results are written to the audit log** for every run that reaches it.

## Evidence

19 tests: each check passing and failing, a secret in each of four places, the size
limit at its boundary, six data-class combinations, and seven runs through the code tool
including a withheld reply that also closes the task.

## Limits

- **The secret scan knows a fixed list of credential shapes,** the same list the static
  check uses. A secret in a shape it does not know passes. Encoding one, for example in
  base64, also passes.
- **The data-class check trusts the tags.** It confirms that what the broker recorded as
  read was handled correctly. It does not look inside the result for personal data. A
  scan of content for personal data is not built.
- **"Its expected format" is only "plain JSON".** The PRD may mean the format the request
  asked for; that needs criteria code can read, which do not exist.
- **Nothing reconciles the result against the report yet.** A result that says "41
  issues" when the run read 3 records passes. That is task 1.7.2.
- **Criteria from the user's request, as opposed to the model,** need the in-app adapter
  (1.9.2), which can see the request.
