# 3.1.2 The dry run for writes

Date: 2026-11-28. Status: **built and tested; switched off in production.** No tool that
writes exists yet, and production does not turn the dry run on. That is task 3.1.3.

FR-42 asks that a script's writes are recorded as one change set without being made, that
the set is checked against policy, quotas and invariants, and that exactly that set is
committed. This record says how that is built.

## How it works

1. **A write is recorded, not made.** When the dry run is on and a script calls a tier-1
   or tier-2 tool, the broker puts the call through every check a read goes through:
   the policy record, the caller rule, the data-class cap, the pinned definition, the
   argument schema, the allowlists, the data-flow rule and the quotas. Then it keeps the
   call and sends nothing.
2. **The script gets a placeholder.** It is `{ dryRun: true, change: n, note }`: fixed
   words and the write's number. It is not the tool's result.
3. **The script runs to its end.** Reads are still made at once. This is the owner's
   decision in docs/decisions/3.1.1-pause-and-resume.md.
4. **The set is checked as a whole**, after the script has ended and every other check on
   the run has passed (the release gate, the cross-check and the reviewer).
5. **The set is put on record** in the audit log (`change_set_planned`), with its hash
   and its exact arguments. If that cannot be written, nothing is sent.
6. **Exactly the recorded calls are sent, in order.** The owner's switches are asked
   again before each one.

The code is `src/broker/change-set.ts` (the record, the hash and the checks),
`brokerHost` in `src/broker/broker.ts` (`writes: "record"` and `commitWrites()`), and the
run path in `src/code-tool/run.ts`. The tests are `test/dry-run.test.ts`.

## What is kept for each write

The tool, its tier, the hash of its pinned definition, and its arguments as canonical
JSON, taken from a copy when the call was checked. That text is what is hashed and what
is sent. A script that changes its arguments afterwards changes nothing.

One hash covers the whole set: every write's tool, definition hash, tier and arguments,
in order. An approval will be bound to this hash (FR-30, task 3.1.5).

## The checks on the set as a whole

These are the invariants. The PRD names none, so this is the first list, and it is
deliberately short.

| Check | If it fails |
|---|---|
| At most 20 writes | `quota_exceeded`. The run is ended at write 21 |
| The arguments together are at most 256 KB | `quota_exceeded` |
| The writes are numbered in the order they were recorded | `policy_denied` |
| Each tool still has a policy record | `policy_denied` |
| Each tool's definition hash is the one recorded | `definition_changed` |
| Each tool's tier and caller rule are unchanged | `policy_denied` |
| Each tool still matches its pin | `definition_changed` |
| No tier-2 action is in the set | `policy_denied`, until approvals exist (task 3.1.4) |
| No call appears twice with the same arguments | `policy_denied` |

Why 20 and 256 KB: the run's limit is 100 calls, and a script that writes more than 20
things at once is past what an owner could read in one approval. 256 KB is 16 times the
size at which arguments are already flagged as unusually large. Both are first values,
with no measurement behind them.

Why no duplicates: the same call twice is far more often a loop that went wrong than
something meant. A script that needs it must vary the arguments.

## What happens to the set

| The run | The set |
|---|---|
| Completed, and every check passed | Committed. The report lists each write under `sideEffects`, and `recordsWritten` counts them |
| Failed, timed out, was refused a call, was held, or was blocked by the reviewer | Dropped. Nothing is sent |
| A check on the set failed | Dropped. The script's result is not handed over, because it was written as if the writes would be made |
| A switch was thrown part-way through committing | Stopped. The writes already made stand and are reported; the rest are not sent |
| A write failed part-way through | Stopped. That write may or may not have been made; none after it is sent |

The set is committed once. A second try sends nothing.

## Limits

1. **It is not one transaction.** GitHub has no way to make several calls succeed or
   fail together. A set can stop half-made. The report says which writes were made, and
   nothing is undone. Undoing is the compensation step in task 3.1.3.
2. **A write that failed may have been made.** A call can fail after the other side has
   acted on it. Making a retry safe is task 3.1.7.
3. **A script cannot use a write's result.** It gets the placeholder. The model is not
   given the tool's answer after the commit either; only that the write was made. How
   the model learns, say, a new issue's number is not designed.
4. **A tier-2 action drops the whole set.** There is nowhere to ask for approval yet.
5. **Nothing the model reads describes the dry run.** The `code` tool's description and
   the contract version are unchanged, because production behaves as before. Task 3.1.3
   must change both, and that change needs the live known-answer checks.
6. **A dry-run write is counted against the tool's daily quota when it is recorded**,
   and the count is not given back if the set is dropped.
7. **The checks at commit read the policy through the run's short memory** of it, as
   every call in a run does. A change made in the last moments may not be seen.
8. **Committing has no time limit of its own.** It runs after the script's 30 seconds.
9. **The data-flow rule is asked when a write is recorded**, not again at commit. The
   arguments are fixed at that moment, so what a script reads later cannot reach them.
10. **No real tool has been through it.** Every test uses made-up tools. The adversarial
    suite has no case for the dry run yet.
11. **Not reviewed by a second model family or a person.** The paid human review (G.10)
    comes before any write runs in production.

## What changes now

Nothing in production. `src/service.ts` does not pass `writes: "record"`, and a broker
built without it refuses a script's call to a tier-1 or tier-2 tool exactly as before.
A test asserts that for the broker; none asserts it for `src/service.ts` itself.
Task 3.1.1's owed test is here: a script with a write runs to its end with the write
recorded and not made.
