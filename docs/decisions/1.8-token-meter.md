# 1.8.1 and 1.8.2 The token meter

Date: 2026-11-23. Requirement: FR-19 and the PRD's token metering table. Status: **done
and tested in memory.** Records went nowhere durable when this was written; since task
2.3.1 production keeps one row per run (see Limits).

## What it measures

One record per run, every figure an estimate:

| Measure | How it is counted |
|---|---|
| Script tokens | The script the model wrote |
| Returned tokens | The final value sent back, or the error message |
| Kept-out tokens | Every tool result that answered, which stayed in the sandbox |
| Discovery tokens | What `search()` and `describe()` returned |
| Definitions not loaded | Typings for the whole catalog, minus typings fetched through `describe()` |
| Estimated saving | Kept-out plus definitions not loaded, minus script, returned and discovery |

The saving can be negative. A small task can cost more as a script than as direct calls,
and the meter says so.

## The three levels

- **Off.** No tokenizer runs, the catalog is not read and nothing is written. Tested
  with a tokenizer that counts how often it is called.
- **Summary.** One record per run.
- **Detailed.** The same, plus the size of each tool result in bytes and tokens. Sizes
  only: the test checks that no content reaches the record.

## What it must not do, and does not

- **It adds nothing to what the model sees.** The reply is identical at all three
  levels. Tested by comparing replies.
- **It cannot fail a run.** A sink or tokenizer that throws loses the figure and nothing
  else. Tested both ways.
- **It is separate from the audit log.** The log is the same at every level.

## A shortfall against the PRD

The PRD says script tokens are "counted with that model family's tokenizer". **No real
tokenizer is bundled.** Every count uses one rough rule: one token per four bytes.

Why: OpenAI publishes a tokenizer library, which would be a new dependency to vet.
Anthropic publishes none for current models; an exact count means a network call to its
API for every run. Neither seemed right to add without the owner's say.

What it means: the figures are good for comparing one run with another and for seeing
the order of magnitude. They are not good enough to quote as a bill or to compare model
families with each other. Each record names the rule that produced it, and the tokenizer
is a plug-in point, so a real one can be added without touching the meter.

The measured saving, from eval runs with the providers' own usage figures, remains the
only real number. That is task 1.9.5.

## Limits

- **In production each record is written to the platform's log** (`execward_meter`),
  and a row of sizes, counts and labels is kept in the `meter_records` table for 90 days
  (task 2.3.1). The console shows the report grouped by session, project, client and
  model. The in-memory sink is for tests.
- **Only runs that finish are metered.** A run refused before it starts, or one that
  ends in a sandbox fault, writes no record.
- **Discovery tokens count what the script received,** whether or not the model ever
  saw it. A script that searches and returns the list is counted under both discovery
  and returned.
- **The catalog's size is read once** per meter, so a catalog that changes while the
  Worker runs is not re-counted.
- **The default level is summary,** since Gate 1 passed on 2026-11-24
  (`DEFAULT_METER_LEVEL`): a meter built with no level named records one line per run.
  Production builds its meter that way (`src/mcp/production.ts`), so it records at
  summary. The owner console has no setting for the level yet.
