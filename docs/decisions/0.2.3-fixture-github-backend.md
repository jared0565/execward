# 0.2.3 (part 1) Fixture GitHub backend

Date: 2026-11-22. Status: built. The eval tasks themselves (the rest of 0.2.3) are next.

## What it is

The eval needs GitHub tools whose answers never change, so that a task has one right
answer and a check can be automatic. `src/eval/fixtures/` provides that:

- `world.ts` builds an invented organisation, `northwind-labs`, with three repositories
  (`billing-api`, `web-dashboard`, `infra-tools`): 108 issues and pull requests, 120
  commits, 18 releases, 90 CI runs and 15 files. It is generated from a fixed seed, so it
  is identical on every machine and every run.
- `github-backend.ts` answers the 15 read-only tools of the inventory (task 0.1.5) from
  that world, with input schemas, paging, filters and search.

This design was Claude's choice. It was not discussed with the owner beforehand.

## Choices and their reasons

| Choice | Reason |
|---|---|
| Invented data, not recorded real responses | No real person's name or code enters the repo, and nothing is sent anywhere. |
| Generated from a seed, not hand-written | A task's expected answer can be computed from the same data, so answers cannot drift from the fixture. |
| Responses carry GitHub's REST fields and nesting, URL fields included | Token cost of a tool result should be close to the real thing. That is what task 0.2.7 measures. |
| `list_issues` returns pull requests too | GitHub does. A model that forgets this miscounts, on the fixture as in life. |
| File contents returned as text, not base64 | A connector would decode them for a model. Otherwise the code arm would win by decoding, which measures the wrong thing. |
| Search supports a stated list of qualifiers and refuses others with a 422 | A silently ignored qualifier would give a wrong answer that looks right. |
| Arguments checked with zod; the JSON Schema offered to the model is derived from the same schema | One definition, so the schema a model sees cannot disagree with what is accepted. |

The response shapes were written from knowledge of GitHub's REST API, not copied from live
responses, and were not compared field by field with GitHub's documentation. They are close
in size and structure, not guaranteed identical.

## Real check

`npx tsx scripts/eval-one.ts --each-route`, 2026-11-22. Task: count the open issues in
`northwind-labs/billing-api`, excluding pull requests. All 15 tools were offered.

| Model | Route | Correct | Turns | Tool calls | Input tokens | Output tokens | Cost |
|---|---|---|---|---|---|---|---|
| Claude Haiku 5.5 | OpenRouter | yes | 2 | 2 | 39,956 | 485 | $0.00424 reported |
| Claude Haiku 5.5 | Anthropic | yes | 2 | 2 | 39,975 | 518 | $0.00426 estimated |
| GPT-6 Luna | OpenRouter | yes | 2 | 1 | 23,114 | 106 | $0.00274 reported |
| GPT-6 Luna | OpenAI | yes | 2 | 1 | 23,114 | 167 | $0.00239 estimated |

Total $0.0136. What this shows:

- Both providers accept all 15 tool schemas, through OpenRouter and directly.
- One list-style task costs about a quarter to half a cent on these models. At that rate
  the 600-run baseline is roughly $2 to $6, in line with the earlier estimate of $3 to $7.
  One task is still a thin basis; the first pass of the full suite will firm it up.
- Almost all tokens are the tool result (one or two pages of issues), not the 15 tool
  definitions. That is the pattern task 0.2.7 is looking for.

One thing not yet explained: for GPT-6 Luna, the cost OpenRouter reported ($0.00274) is
16% above tokens times the listed price ($0.00236). For Haiku the two match exactly, and
they matched for Luna on the earlier tiny task. The runner counts the reported figure
towards the spend cap, so the cap stays safe; the cause should be found during 0.2.5 by
logging OpenRouter's usage details.
