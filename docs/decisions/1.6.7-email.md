# 1.6.7 Sending the link-only emails

Date: 2026-11-24. Requirements: FR-44, FR-49, flag 11. Status: **working. The owner
sent the test email from the live console on 2026-11-24 and it arrived in the inbox,
not in spam. No real alert has been sent, because nothing raises one in production
yet.**

## The decisions

The project owner chose, on 2026-11-23 and 2026-11-24:

- **Cloudflare's email sending,** not an outside provider. No second company sees the
  mail, and there is no key to hold.
- **A subdomain to send from.** `execward.com` already receives mail, and had no DMARC
  record. Onboarding a domain for sending adds one, which could change how the domain's
  own mail is treated. Sending from `notify.execward.com` keeps every new record under
  that name.

## What was set up on Cloudflare

A sending subdomain, `notify.execward.com`. Cloudflare's preview was read before
creating it. It added six DNS records, all under that name: three MX and one SPF record
for bounces, one DKIM key, and a DMARC record that rejects mail failing the checks. No
existing record was changed or removed; the record list was compared before and after.

## How it works

- **One sender.** The Worker's email binding may send only as
  `alerts@notify.execward.com`. The configuration check refuses any other sender, a
  second one, or a binding with no limit.
- **One recipient.** The owner's address, the same secret the console uses
  (`OWNER_EMAIL`). It is fixed when the mailer is built; nothing in a request or an item
  can choose it. A value that is not one plain address means email is not set up.
- **What an email says** is unchanged (`src/console/notify.ts`): that something is
  waiting, and a link. No project, tool, error text or figure.
- **The link carries nothing.** It used to end in the item's ID. It now leads to the
  console's one page, where the queue is, so not even an ID is in the email.
- **When.** An urgent item is emailed on the timer's first run after it is raised, so
  within five minutes, then again every hour while it is open. Everything else waits
  for the daily digest.
- **Reminders are decided from the clock alone.** A Worker on a timer remembers nothing
  from one run to the next. The reminder logic used to remember when it last wrote, in
  memory; on the timer that would have sent a reminder every five minutes for any item
  over an hour old. An email is now due on the first run after the item appears, and
  then on each run in which the item's age passes a whole number of hours.
- **A test button** in the console sends one email that says it is a test.

## Cost

Read on Cloudflare's pricing page on 2026-11-24: 3,000 emails a month are included in
the Workers Paid plan the account already has, then $0.35 per 1,000. ExecWard sends a
few a day at most.

## Evidence

- 14 tests in `test/console-http.test.ts` and those in `test/escalations.test.ts`: the
  one sender and recipient, what is refused as a recipient, the test email, who may
  send it, reminders on a timer that remembers nothing.
- On Cloudflare: the subdomain's DNS status reads "ready".
- For real: the owner pressed "Send me a test email" on the live console on 2026-11-24.
  It arrived in the inbox of the owner's address, from `alerts@notify.execward.com`.
  This is the owner's report; ExecWard does not read deliveries back.

## Limits

- **A reminder can be missed or doubled.** If a timer run is skipped, the reminder due
  in it is not sent; if a run happens twice, it is sent twice. The item stays in the
  queue either way.
- **Nothing raises an item in production yet,** because the `code` tool is not served
  there. So no urgent email, reminder or digest has been sent for real.
- **An urgent email can take up to five minutes,** the gap between timer runs. The
  queue could send the moment an item is raised, but then the timer's first email must
  be switched off, or it is sent twice.
- **The binding is not limited to one recipient.** Cloudflare can fix a binding's
  recipient, but only by writing the address in the configuration, which is public.
  The limit is in the code instead.
- **Delivery is not confirmed by ExecWard.** A bounce is handled by Cloudflare and is
  not read back.
