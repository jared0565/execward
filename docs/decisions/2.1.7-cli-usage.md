# 2.1.7 Which usage figures each CLI can hand to the stats report

Date: 2026-11-24. Traces to: PRD "Open questions". Status: **answered from the
vendors' documentation. Nothing here was tried on a machine.**

## The question

ExecWard estimates the tokens a run saved. The real figures, counted by the model
provider, are held by the CLI. Which of them can each CLI give to a report?

## The short answer

- **Neither CLI gives usage to an MCP server.** MCP has no field for it. ExecWard
  cannot receive these figures on the connection it already has.
- **Both can export them from the user's machine,** if the user turns that on. The
  common route is OpenTelemetry, a standard way of sending measurements to a collector.
- **Only Claude Code documents which MCP server and tool a figure belongs to.** Codex
  documents no such link.
- **No shared ID joins a CLI's figures to an ExecWard run.** They can be matched by
  time and model name only.

## Claude Code

| Route | Turned on by | What it gives | Detail |
|---|---|---|---|
| OpenTelemetry metrics | `CLAUDE_CODE_ENABLE_TELEMETRY=1` and `OTEL_METRICS_EXPORTER` | `claude_code.token.usage` with `type` of `input`, `output`, `cacheRead` or `cacheCreation`; `claude_code.cost.usage` | Added to after each request. Carries `model` and `session.id` |
| OpenTelemetry events | The same, with `OTEL_LOGS_EXPORTER` | `api_request`: `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `cost_usd`, `model`, `request_id` | One per request |
| Non-interactive run | `claude -p --output-format json` | `session_id`, `total_cost_usd`, a cost breakdown per model | One per run |
| Status line | A `statusLine` command in settings | Session cost, and the token counts of the latest reply | No history |
| `/usage` | Typed by the user | Session totals per model; for subscribers, an approximate share per MCP server | For reading, not export |

The metrics and events carry `mcp_server.name` and `mcp_tool.name`. They show the real
names only when `OTEL_LOG_TOOL_DETAILS=1` is set; otherwise a general word. The
documentation does not say exactly which request is given a tool's name.

Telemetry cannot be turned on from a repository's settings file. The user sets it in
their own settings or shell. Hooks carry no usage figures.

## Codex

| Route | Turned on by | What it gives | Detail |
|---|---|---|---|
| Non-interactive run | `codex exec --json` | `turn.completed` with `usage`: `input_tokens`, `cached_input_tokens`, `output_tokens`, `reasoning_output_tokens` | One per turn |
| OpenTelemetry | An `[otel]` section in `config.toml` with an exporter | `codex.sse_event` carries token counts when a reply completes; a `turn.token_usage` measure with `token_type` | Field names only partly documented |
| `/status` | Typed by the user | "Current token usage" | For reading, not export |

Nothing documented ties a figure to an MCP tool call. The `notify` program carries no
token fields. Whether saved session files hold token counts is not documented.

## What this means for the stats report (task 2.3.1)

- A report can show ExecWard's own estimate for every run today, grouped by the model
  name from task 2.1.6.
- Showing provider-counted figures beside it needs the user to export them, and
  something to receive them. That is a new part: a collector address, or a file the
  user uploads. It is the owner's decision in 2.3.1, because it adds a service and
  sends usage data off the user's machine.
- Costs from both CLIs are estimates at list price. Token counts are the provider's.

## Limits

- **Read, not run.** The source is the vendors' documentation as read on 2026-11-24.
  Several pages were long and read in part, through a summarising tool. Names quoted
  here should be checked against a real export before any code relies on them.
- **Codex's pages had moved.** The addresses redirected to another site, which was
  read.
- **Both CLIs change often.** This answer has a date and will age.
