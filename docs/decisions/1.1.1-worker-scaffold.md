# 1.1.1 The core as a Worker, with an allowlist of bindings

Date: 2026-11-22. Requirements: FR-23 (pinned runtime), FR-24 (the server is confined).
Threat-table row 5 (unconfined server process).

## What exists

This section and the table below were brought up to date on 2026-11-27. The scaffold of
2026-11-22 had one binding, answered only `GET /health`, and was not deployed.

- `wrangler.jsonc`: the Worker's configuration. Four bindings: the Worker Loader
  (`LOADER`), which runs model-written scripts in a Dynamic Worker; the database (`DB`);
  the backup bucket (`BACKUPS`); and the email sender (`EMAIL`). Also two addresses and
  one timer.
- `src/worker.ts`: the entry point. It answers `GET /health` with the version, serves the
  owner console and the MCP server, and runs the housekeeping timer.
- `src/worker/bindings.ts`: the allowlist, in code.
- `src/worker/config-check.ts`: checks the configuration against the allowlist.

On 2026-11-22 nothing was deployed, and no Cloudflare account, plan or credential was
used. The first deployment is task 1.1.5.

## How a new binding is stopped

On Workers, a binding is the only way the code reaches anything: a database, a secret,
another service. So the list of bindings is the whole of the server's reach, and FR-24
comes down to keeping that list short and making changes to it visible.

The check is **default deny**. Every top-level key in `wrangler.jsonc` must be named in
the allowlist. A key that is not named fails the tests, and CI with them, whatever it is:

- any binding section (KV, D1, R2, services, Durable Objects, queues and the rest);
- `vars`, which would put values in the environment;
- `env`, named environments, which can carry bindings of their own;
- any route other than the two in `ALLOWED_ROUTES`, and any timer other than the one in
  `ALLOWED_TRIGGERS`;
- a kind of binding that does not exist yet.

A list of known binding types would have missed the last one. Tests cover each of these.

Also fixed by the check:

| Setting | Must be | Why |
|---|---|---|
| `compatibility_date` | `2026-11-13`, the same in the config and in code, and not in the future | Pins runtime behaviour (FR-23). A recent date the pinned Wrangler's runtime accepts without warning |
| `compatibility_flags` | none | Each flag changes what the runtime allows; none is needed yet |
| `workers_dev`, `preview_urls` | `false` | No workers.dev or preview address. The Worker answers only at `console.execward.com` and `mcp.execward.com`, each behind Cloudflare Access |
| `routes`, `triggers` | exactly `ALLOWED_ROUTES` and `ALLOWED_TRIGGERS` | Another address would be a way in that Access does not guard |
| `observability` | exactly `{ "enabled": true }` | The run metrics go to the platform's log (task 1.9.3) |
| `upload_source_maps` | `true` | So an error in the log points at a line of this repository's code |
| `send_metrics` | `false` | No usage data goes to the tool's vendor from this repository. Confirmed with `wrangler telemetry status` |
| `worker_loaders` | exactly one, named `LOADER`, with no other settings | One of the four allowed bindings; the other three are fixed the same way, each with its settings |

To add a binding later: change `wrangler.jsonc` and `ALLOWED_BINDINGS` in the same pull
request, and say why. That makes it a reviewed decision instead of a config edit.

## In CI

- The tests above run in the required job.
- `npm run build:worker` runs `wrangler deploy --dry-run`: it bundles the Worker and
  validates the configuration, and deploys nothing. A configuration Wrangler rejects cannot
  merge.

## Dependency added

`wrangler` 4.166.0 as a pinned development dependency (69 packages with its own
dependencies, all from the npm registry with content hashes; the supply-chain check
passes). It is a build tool, not part of what runs in production.

## Limits

- **This checks the configuration file, not the deployed Worker.** Someone with access to
  the Cloudflare dashboard could add a binding there. Task 1.1.6 tests the deployed Worker
  from the inside; G-level access to the account is the owner's alone.
- **`Env` is written by hand.** Cloudflare's advice is to generate it with
  `wrangler types`. That needs the Workers runtime types, which clash with the Node types
  the rest of the repo uses under one TypeScript config. The plan was for task 1.2 to
  switch to generated types; it did not. The runtime types the code needs are declared by
  hand in `src/executor/cloudflare-workers.d.ts`.
- **The handler is tested as a plain function.** Since task 1.2 the code is also tested
  inside the local Workers runtime (`test/workers/`) and on a deployed test Worker
  (`test/deployed/`).
- **Nothing here needs the paid plan.** Running a Dynamic Worker with real limits does
  (task 1.2), and that is the next point where the owner is asked.
