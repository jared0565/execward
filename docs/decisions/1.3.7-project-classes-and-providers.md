# 1.3.7 Project data classes and approved providers

Date: 2026-11-23. Requirements: FR-38, FR-32. Builds on the provider findings of task
0.1.6 and the personal-data duties of 0.1.7. Status: **done.** Sign-in is now
built (Cloudflare Access, task 2.1.2), but it says who the caller is, not which provider
route they are on, so every caller still counts as the unknown route. Brought up to date
on 2026-11-27.

## The rule

Whatever a script returns goes to the model that called the `code` tool, and so to that
model's provider. A run may handle **the lower of two limits**:

1. **The project's data class,** set by the owner. A project with no record is `public`;
   on the served MCP route it is not run at all (task 2.3.3). Since task G.13 the
   project's client can lower the class further, or ask for no AI use at all
   (docs/decisions/G.13-client-choice.md).
2. **What the caller's provider route is approved for:**

| Route | May receive up to |
|---|---|
| Anthropic API, organisation account under the Commercial Terms | Confidential |
| OpenAI API, business account under the Services Agreement | Confidential |
| ChatGPT Business or Enterprise | Confidential |
| Claude Free, Pro or Max, including Claude Code signed in with one | Internal |
| ChatGPT Free, Plus or Pro, including Codex signed in with one | Internal |
| Unknown | Internal |

Approved routes move up to client personal data only when gate G.7 is cleared.

## How it is enforced

- **At the call.** A tool whose data class is above the run's limit is refused before
  anything is read, and the run ends. The data never enters the sandbox.
- **In discovery.** `search` and `describe` do not show such tools, so a model is not
  led towards calls that will be refused.
- **At the reply.** Output hygiene (task 1.3.6) uses the same limit as a second layer.
- **In the log.** Every run's first entry records the provider route and the limit.

## The client-data gate

`CLIENT_DATA_GATE.cleared` is `false`. While it is:

- a project cannot be set to client personal data; writing such a record is refused;
- a record that says client personal data anyway (written straight into the database,
  for example) is treated as confidential;
- no provider route may receive client personal data.

Clearing the gate is one line in `src/broker/exposure.ts`, and belongs in the pull
request that records G.7 as done: the DPIA, the transfer risk assessment and the
sub-processor checks.

## One place where nothing is optional

The broker, quotas, audit log and data-class cap were built so each can be tested alone,
which left several of them accepting being left out. `src/service.ts` is now the single
place that puts them together, and there every one is required. Any route that serves
the `code` tool must go through it. It is tested end to end in memory.

## Choices

- **Refuse at the call, not only mask at the reply.** Refusing before the read means the
  data is never in the sandbox at all.
- **Anything not recognised is the unknown route.** A route is never guessed upwards.
- **The route must come from sign-in, never from the request.** A caller cannot be asked
  how it is signed in and believed.
- **Fail closed.** If the project's record cannot be read, the run does not start.

## Evidence

22 tests: every route with the gate open and shut, the gate refusing a client-personal
project, the lower-of-two rule in eight combinations, eight unrecognised routes, the
broker's cap, and eight runs through the whole service.

## Limits

- **Nothing establishes the route yet.** Sign-in (task 2.1.2) does not, so every caller
  is `unknown` and capped at internal data. GitHub source files are classed confidential, so no run
  can read a file until a caller's route is established as approved.
- **ExecWard cannot verify how a client is signed in to its own provider.** Sign-in can
  establish which client is calling; whether that client's account is on commercial terms
  is something the owner asserts when registering it. Task 0.1.6 already asks the owner
  to confirm the Anthropic account is an organisation account.
- **Project records are in the `projects` table.** A project's class is set by
  `npm run setup:github` or `npm run repo:setup`. The console has no action for it; it
  records the client's choice only.
- **A refused call ends the run.** A model that reaches for a file in an internal project
  gets a final `policy_denied`, not a hint to try something else. Hiding such tools from
  discovery is what should keep that rare.
- **The provider findings are from 2026-11-22** and were read through a web-reading
  agent; terms change. The table above should be re-checked before real client data.
