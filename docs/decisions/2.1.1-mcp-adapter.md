# 2.1.1 The MCP adapter

Date: 2026-11-24. Requirement: FR-10. Status: **done. Built, and reached over the internet
on the test Worker by a test client, by Claude Code and by Codex. Not served from
production: that waits for sign-in (task 2.1.2).**

## What it is

`src/mcp/adapter.ts` serves one tool, `code`, as a remote MCP server over Streamable
HTTP. A call goes through `codeToolService` and nothing else, so every control of the
core applies. The reply is given to the model as one block of text inside the
untrusted-output markers (FR-36), with no second structured copy beside it.

## Decision by the project owner: the MCP project's own library

The protocol has two revisions in use: 2025, with a handshake, and 2026-07-28, with
none. The owner chose the MCP project's server library over hand-written handling and
over Cloudflare's larger wrapper.

| | |
|---|---|
| Added to what runs in production | `@modelcontextprotocol/server` 2.4.0 and its `@modelcontextprotocol/core` 2.4.0. Their only other need is `zod`, already used |
| Added for tests only | `@modelcontextprotocol/client` 2.4.0, which brings `eventsource`, `eventsource-parser`, `jose` and `pkce-challenge` |
| Runtime packages before and after | 3, now 5 |
| Installed | At exact versions, with install scripts off. They are in the lockfile and the SBOM and pass the supply-chain check |

One handler serves both revisions. It keeps nothing between requests: no session, no
stream to listen on. `GET` and `DELETE` are answered 405.

## What it does not do

- **No sign-in.** The library never reads a credential from a request, and nor does the
  adapter. Whoever mounts it must already know who is calling and passes that in.
  Sign-in for model clients is task 2.1.2. Until then it is mounted only on the test
  Worker, behind that Worker's secret.
- **The provider route is fixed by the mount,** not taken from the request. A field
  for it in a call is refused, as any field outside the contract is.
- **Attempts are counted per call,** not per session. Refusing a third attempt in a
  session is task 2.1.5 and needs a store, since nothing is kept between requests.
- **Code Mode off still lists the tool.** The call is refused with `code_mode_off`.
  Removing the tool from the list and offering the wrapped tools directly is task 2.1.4.
- **The read-only hint on the tool is a hint to the client,** not a control.

## Evidence

- `test/mcp-adapter.test.ts`, 12 tests, with the library's own client: the tool list;
  a call and its caller; the untrusted block, including a planted closing tag; errors
  and refusals marked as errors; calls outside the contract refused before the
  service; a 2025 client's handshake, list and call written out by hand; nothing kept
  between callers.
- `test/deployed/mcp.deployed.ts`, 5 tests, on Cloudflare with every store on the
  database and the invented GitHub: a script calls a tool and the answer comes back;
  a script the static check refuses comes back as an error; a project with no record
  gets nothing above public data; no secret, no answer.

## A wrong test, caught

The first version of one deployed test expected a run for an unknown project to be
refused. It is not, by design: no record means the most cautious class, public
(FR-32). The test now checks that rule.

## The two CLIs connecting

Done on 2026-11-24, with the owner's go-ahead for a one-off check with nothing saved.
Each CLI was pointed at the test Worker's `/mcp` path with that Worker's secret, and
asked to call `code` once with the script `return 6 * 7;` for the project `eval`.

| CLI | How it was given the server | Result |
|---|---|---|
| Claude Code, with a small Claude model | A settings file made for the one run and deleted after it | Called `code`; answer 42 |
| Codex CLI 0.169.0, with its default model | Settings passed on the command line; the secret through an environment variable | Listed `code` as the server's only tool; called it; answer 42 |

Limits of this check:

- One run each, one trivial script. It shows the connection and one call, not a task.
- Claude Code was allowed that one tool and did not report the server's full list. The
  list is shown by the test client and by Codex.
- Which protocol revision each CLI spoke was not recorded.
- Neither CLI's own settings were changed, so neither stays connected. Connecting them
  for real use waits for sign-in.
