# 3.1.1 Pause and resume

Date: 2026-11-28. Status: **chosen by the project owner; the test is still owed.**

A script that needs the owner's approval for a tier-2 action must pause, then carry
on once the owner answers. This record says how.

## The question

Task 3.1.1 asks how a script pauses for the owner's approval of a tier-2 action and
carries on afterwards. The PRD named two ways:

- replay the script with captured values, or
- a broker that holds the call open until the owner answers.

The PRD's risk table called the second one "my inference, untested".

## The decision

The owner chose a third way on 2026-11-28: **approve the stored writes.**

The dry run the PRD already requires (FR-42, task 3.1.2) records a script's writes as
one change set, without doing them. So a script always runs to its end before anything
is written. Nothing has to be frozen mid-script.

When the change set holds a tier-2 action:

- the `code` call returns `paused` with an `escalation_id`;
- the change set waits in the owner console's queue;
- **approve** commits exactly that change set;
- **reject** drops it;
- no answer within 24 hours takes the safe default the PRD sets for tier 2, which is
  saved as a draft.

## Why this way

- The PRD's own tier table already describes it: a tier-2 action is "Paused with the
  run report and the exact change set".
- It matches how `paused` already works. Since contract version 1.7.0 a run whose
  critical figure disagrees ends, returns `paused` with an escalation ID, and waits in
  the queue (`src/code-tool/run.ts`).
- Approval binds to the exact call (FR-30, task 3.1.5). What is approved is the stored
  change set, so a hash of it is the thing approved, and only it is committed.
- It works with the PRD's 24-hour wait and its rule that approvals happen only in the
  owner console.
- No script is ever run twice, so no script has to behave the same way twice.

## The options

| Option | How it works | Why not, or why |
|---|---|---|
| 1. Approve the stored writes | The script runs to its end. Its writes are recorded as one change set. The owner approves or rejects that set. | **Chosen**, for the reasons above. |
| 2. Replay from a log | The script stops at the gated write. After approval it runs again from the top. Earlier calls are answered from a saved log, and it carries on. | Not chosen. It needs bans or captures in the static check and the sandbox, a way to refuse a second run that differs, and it is the most new code and new attack surface. Its one advantage: a later write in the same run can use a real earlier result. |
| 3. Hold the call open | The script waits at the write until the owner approves. | Not chosen. The waiting call lives only in memory, so a dropped connection or a restart loses the run. A run's time limit is 30 seconds. A waiting run holds one of a project's 2 concurrent run slots. The model's client will not wait 24 hours. |

Notes on the two options not chosen:

- **Replay.** Cloudflare's own Code Mode has done this since Agents SDK v0.16.1
  (2026-06-16). Its durable runtime gained `execute()` for MCP servers on 2026-07-22.
  Cloudflare's docs say logged calls "must therefore be sequential and deterministic",
  and that model code must not use `Promise.all` for them. Its Workflows rules warn
  against `Date.now()` and `Math.random()` outside steps.
- **Hold open.** Cloudflare sets no hard time limit on an HTTP request while the client
  stays connected, and gives requests up to 20 minutes to finish during a runtime
  update. So the platform's own time limit is not what rules this option out. The
  reasons in the table are. The client's exact time limit was not checked.

These were read through Cloudflare's documentation search on 2026-11-28, as excerpts,
not whole pages.

## Limits of the decision

1. A script cannot use a write's real result later in the same run, for example the
   number of an issue it has just asked to create. The model runs a second script after
   the approval. How a dry-run write answers the script (a placeholder, and what shape)
   is for task 3.1.2 to settle.
2. How the model learns the outcome of an approval is not designed yet. Task 3.1.6
   covers the paused-run ID it would present.
3. Data read by the script may be stale by the time the owner approves. The PRD's answer
   is that an approval older than 15 minutes re-runs the checks (task 3.1.5).
4. Nothing is built or tested yet. The task's test moves to task 3.1.2: its tests must
   show a script with a write running to its end, with the write recorded and not done.
   Task 3.1.1 stays In progress until then.
5. Replay is not ruled out for later. It would be reconsidered only if real scripts turn
   out to need a write's result mid-run.
6. The PRD's risk row "Replay divergence" and task 3.1.1's wording still name only the two
   older ways. TASKS.md is updated with this record. The PRD row is the owner's to change.

## What changes now

Tasks 3.1.2 (dry run) and 3.1.4 (approval in the console) are built on this choice.
Nothing is turned on. No tool that writes exists yet.
