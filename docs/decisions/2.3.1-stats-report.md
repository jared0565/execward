# Task 2.3.1: the stats report

Decided and built 2026-11-25. Requirement: FR-20. Builds on the token meter
(`1.8-token-meter.md`), the model label (`2.1.6-model-label.md`) and the net saving
(`2.2.5-net-saving.md`).

## The owner's decision, 2026-11-25

Until now each run's meter line went only to the platform's log, which is not kept. The
owner chose a **new database table** to hold them, over running totals in the existing
counters (which cannot group by session) and over leaving the task for later.

## What is kept

One row per metered run, in `meter_records` (`migrations/0006_meter_records.sql`):

| Column | What it is |
|---|---|
| `run_id`, `at` | The run and when it ended |
| `project` | The project the call named |
| `session`, `client`, `model` | What the client said about itself |
| `kind` | Looked for tools, called tools, or neither (as in task 2.2.5) |
| `estimated_saving` | The meter's estimate, which may be negative |
| `verified`, `verification_tokens` | Whether the reviewer was asked, and the provider's count of what that used |

Labels and counts only: never a script, a result or any other content. A run is kept
once, however often it is written. Rows older than 90 days are removed by the daily
round. The table is not in the backup: losing a row loses one line of a report.

## The report

The last 30 days, grouped four ways: by session, project, client and model. At most 50
lines a grouping, busiest first. The owner's console shows it in a new section,
"Stats", from a new address, `/console/stats`, behind the same sign-in as the rest.

**Estimated and measured are kept apart** in every line, as FR-20 asks:

- estimated: the meter's saving, from a rough rule of one token per four bytes;
- measured: verified runs and the tokens verification used, as the provider counted.

**No measured saving is shown**, and the report says why. A measured saving needs the
same task done both ways with the provider's usage figures for each, which only the
eval does. A production run is done one way.

## Session

The server issues no sessions. A client that keeps one of its own and sends the MCP
session header has its runs grouped under it. Every other run is grouped by UTC day
(`day:2026-11-25`). So for most clients today, "by session" is "by day".

## Release order

The migration is applied to production before the code is deployed. It only adds a
table. Code running without the table would leave runs unaffected, since a failed write
loses the row and nothing else, but the console section would say the stats could not
be read.

## Checked

Tests in memory, and one in a real local D1 database in the Worker runtime that writes,
groups and trims rows. The code was broken eleven ways in turn and all eleven were
caught, three of them in the database's own SQL.

## Limits

- **Client, model and session are the client's own words**, unchecked. They label a
  line and decide nothing.
- **Only metered runs leave a row**: not a run refused before it starts, nor one that
  ends in a sandbox fault.
- **Runs before this was deployed are not in it.**
- **Nothing breaks the figures down by kind of run here**; the net-saving section does
  that.
- **Not yet seen on production.**
