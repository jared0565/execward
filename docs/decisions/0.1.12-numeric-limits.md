# Task 0.1.12: numeric limits

Set 2026-11-22. The values live in `src/limits.ts`; `test/limits.test.ts` checks they are
consistent with each other and with Cloudflare's ceilings. These are starting defaults chosen
by reasoning, not by measurement. The Phase 0 baseline (task 0.2.5) will show whether real
tasks fit; change the numbers there and in this file together.

## Per run

| Limit | Value | Why |
|---|---|---|
| CPU time | 1,000 ms | Scripts orchestrate tool calls and filter JSON, which is light work. Cloudflare's own code-interpreter example uses 50 ms. One second leaves room for large results and still ends a busy loop quickly. |
| Wall-clock time | 30 s | A GitHub read takes a few hundred milliseconds, so 30 s covers several dozen sequential calls. Enforced by ExecWard, since the platform has no wall-clock limit. |
| Host calls | 100 | Tool, `search()` and `describe()` calls together. Enough to page through results; low enough that a looping script stops early. Enforced by the executor, in the host Worker. |
| Final result size | 32 KB | About 8,000 tokens. The point of Code Mode is to keep bulk data out of the model's context, so the final value must stay small; larger values are cut with a notice (FR-5). |
| Memory | 128 MB | Fixed by Cloudflare. Cannot be lowered. |

## Before a run and per call

| Limit | Value | Why |
|---|---|---|
| Script size | 64 KB | Far above any hand-sized orchestration script. A larger one is more likely smuggled data than logic (FR-33). |
| Large argument flag | 16 KB | A read-only GitHub call takes arguments of a few hundred bytes. Sixteen kilobytes in one argument suggests data being carried out, so it is flagged (FR-29). |
| Tool result size | 1 MB | Lets a script fetch a sizeable listing and filter it inside the sandbox, while staying far below the memory ceiling (FR-35). |

## Per project

| Quota | Value | Why |
|---|---|---|
| Runs per minute | 10 | One agent session rarely needs more; a burst above it is more likely a loop. |
| Concurrent runs | 2 | One owner, one tenant. Cloudflare allows 4 Dynamic Workers in flight per request. |
| Runs per day | 500 | Ties the run quota to the daily spend cap: 500 runs at $0.002 is $1. |
| Upstream calls per day | 10,000 | Well under GitHub's 5,000 requests an hour, and a fifth of the worst case the other limits allow. |

## Circuit breaker and spend

| Limit | Value | Why |
|---|---|---|
| Upstream errors in a row | 5 | Distinguishes an outage from one bad call. |
| Policy denials in a run | 3 | The first denial already escalates and is never retried (FR-41). Three ends a script that keeps probing. |
| Platform spend per day | $1 | Matches the run quota. |
| Platform spend per month | $20 | A ceiling for a single-owner deployment, on top of the $5 plan. |

Model spend for verification is capped separately: $1 a day and $10 a month for the whole
installation (`VERIFICATION_BUDGET`, the owner's decision of 2026-11-25, task 2.2.1).

`src/limits.ts` has since gained values set by later tasks, which this file does not
list: the retry limit (`SELF_CORRECTION`, task 1.7.3), the cross-check limits
(`CROSS_CHECK_LIMITS`, task 2.2.2) and the audit log's retention (`RETENTION`, task 1.4.4).

## Not set here

The Gate 1 success threshold stays with task 0.2.6. The PRD proposes "within 5 points of direct
calls"; that task confirms or changes it once the baseline exists.
