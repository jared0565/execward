# 2.1.2 Sign-in for model clients

Date: 2026-11-24. Requirements: FR-25, FR-10. Status: **built, tested and deployed.
Not yet seen working with a real CLI: that needs the project owner to sign in once
from Claude Code or Codex. The task stays In progress until then.**

## Decisions by the project owner, 2026-11-24

1. **Sign-in is Cloudflare Access,** as for the console, not a sign-in server of
   ExecWard's own.
2. **The MCP server's address is `mcp.execward.com`,** separate from the console's.
3. **Access is used for who the caller is; ExecWard enforces what a caller may do.**
   Made after it was found that Access cannot do three things the task's wording asks
   for (below).

## How it works

The MCP address has its own Access application, with managed OAuth switched on. A CLI
that asks for the address with no token is told where to sign in. It opens a browser;
the owner signs in with the emailed code and the authenticator; Access gives the CLI a
token. On each request Access checks that token and hands the Worker `ctx.access`.

The Worker never sees the CLI's token, and never passes any token on. What it reads is
`ctx.access`, which only the platform can set.

| Setting on the Access application | Value |
|---|---|
| Who is allowed | The owner's address only |
| Second factor | Required |
| Token a CLI holds | Valid 15 minutes; renewed quietly for up to 7 days, with the policy checked again each time |
| Which clients may register | Any, but only with a return address on this computer (localhost or loopback) |

## What the Worker checks (`src/mcp/production.ts`), each failing closed

- The request came to `mcp.execward.com`, and to `/mcp`. Nothing else is answered at
  that address: no console, no health check. And `/mcp` is answered at no other address.
- It did not come from a web page. A CLI sends no `Origin` header; a page does. Any
  request with one is refused, so a page the owner visits cannot drive the tool.
- Access authenticated it **for the MCP application.** The console and the MCP server
  have different audiences, so a sign-in to one is not a sign-in to the other, in
  either direction. This is the test "a token issued for another service is rejected".
- The person is the owner. A service token is refused.
- Until both settings are stored, everyone is refused.

## What Access does not give

| The task asked for | What there is instead |
|---|---|
| Scopes that start read-only and step up for side effects | Access has no permission levels. What a client may do is decided by ExecWard's policy table on every call. In Phase 2 every tool is read-only. From Phase 3, anything with a side effect needs the owner's approval in the console, which a token cannot give |
| Consent asked per client before proxying | There is no separate "allow this client?" screen. The owner signs in through Access each time a new client is connected, and only a client on the owner's own computer can register |
| A released product | Cloudflare labels managed OAuth as Beta |

The owner chose to go ahead on these terms. The task's test is read accordingly.

## Limits

- **Not yet seen with a real CLI.** In particular, that the platform fills `ctx.access`
  for a request carrying an OAuth token, as it does for a browser sign-in, is taken
  from Cloudflare's documentation and not yet observed.
- **Production has no tools.** No upstream is connected and the policy table is empty,
  so a signed-in CLI can run a script that calls nothing. Connecting GitHub needs the
  production credential, which is the owner's to create.
- **The provider route is "unknown" for every caller,** the most cautious setting, so
  only public data can be returned. Telling the clients apart is task 2.1.6.
- **One person.** The check is "is this the owner". There are no other users.
- **The outbound guard does not read package code.** It follows this repository's own
  files. The MCP library is trusted as a pinned dependency, not inspected by that test.
- **The sandbox module is loaded on first use,** not at start-up, because it exists
  only inside the Workers runtime and ordinary tests must be able to load the Worker.

## Evidence

- `test/mcp-production.test.ts`, 19 tests: the owner is served; an unauthenticated
  request, a console sign-in, another application's sign-in, another person, a service
  token and an unreadable identity are each refused with the tool never reached;
  missing settings refuse everyone; a request from a web page is refused; forged
  headers and a made-up token do nothing; the two addresses serve only their own part.
- On Cloudflare: see the deployment notes in TASKS.md.
