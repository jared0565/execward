# 1.4.5 Backups and restore

Date: 2026-11-23. Requirement: NFR recovery; flag 10. Status: **done. Backup and
restore are built and proven on Cloudflare on the test Worker, and the daily backup runs
on the production Worker (docs/decisions/production-schedule.md).**

## What was built (`src/backup.ts`)

The owner chose Cloudflare R2, object storage in the same account, outside the database.

- **A backup** is one JSON file holding every row of the tables that cannot be rebuilt:
  the policy, the audit log and its anchor, the escalation queue, the owner's switches
  and the project records. Quota counters are left out; they start again from zero.
- **It is named for its day,** `backups/2026-11-23.json`. A second backup the same day
  replaces the first.
- **Its SHA-256 is stored beside it.** After writing, the backup is read back and
  compared before anything older is deleted.
- **Backups older than seven days are deleted** in the same pass. Only files named like
  a backup are touched.
- **Restore** loads a backup into a database whose tables exist and are empty. It
  refuses a backup that does not match its hash, and refuses to write over existing rows.

## Evidence

| Where | What |
|---|---|
| Local runtime, 5 tests | Every table round-trips; a table of 1,100 rows (more than one page); pruning; a changed backup is refused and nothing is written; a missing backup and a non-empty table are refused |
| Cloudflare, 3 tests | The same on a real R2 bucket and a real D1 database: a backup is written, the database is emptied, the backup is restored, and the audit log comes back entry for entry with its hash chain verifying |

So the acceptance test's second half is met: one restore from a backup into a scratch
database succeeds, on the real platform.

## Why seven days

A backup holds the audit log as it was on its day. Text that retention has since removed
(after 7 days), or that an erasure request removed, is still in older backups. Keeping
backups for seven days means removed text can outlive its removal by at most seven days.
A longer keep time gives more recovery and less deletion; this is the owner's to change.

## Limits

- **The first production backup is of empty tables.** The restore that was proven used
  test content on the test Worker.
- **Erasure is not immediate in backups.** A project's deleted logs remain in backups
  for up to seven days. The client notice now says so.
- **The backup is not encrypted by ExecWard.** R2 encrypts at rest. Anyone with access
  to the Cloudflare account can read it, as they can read the database.
- **Same account, same provider.** A backup in R2 survives a damaged or wrongly migrated
  database. It does not survive losing the Cloudflare account.
- **One file, built in memory.** Fine for the sizes expected. A very large audit log
  would need the file written in parts.
- **Restore is a function, not a command.** No tool runs it against production yet.
- **The audit chain proves the restored log is internally consistent,** not that it is
  the latest. A restore from yesterday's backup loses today's entries.
