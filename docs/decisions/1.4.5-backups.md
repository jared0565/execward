# 1.4.5 Backups and restore

Date: 2026-11-23. Requirement: NFR recovery; flag 10. Status: **done. Backup and
restore are built and proven on Cloudflare on the test Worker, and the daily backup runs
on the production Worker (docs/decisions/production-schedule.md).**

## What was built (`src/backup.ts`)

The owner chose Cloudflare R2, object storage in the same account, outside the database.

- **A backup** is one JSON file holding every row of the tables that cannot be rebuilt:
  the policy, the audit log and its anchor, the escalation queue, the owner's switches
  and the project records. Quota counters are left out; they start again from zero.
- **It is named for its day,** `backups/2026-11-23.json`. A second backup the same day
  replaces the first.
- **Its SHA-256 is stored beside it.** After writing, the backup is read back and
  compared before anything older is deleted.
- **Backups older than seven days are deleted** in the same pass. Only files named like
  a backup, or the retry note beside one, are touched. While the kill switch is set no
  older backup is deleted (2026-11-27).
- **Restore** loads a backup into a database whose tables exist and are empty. It
  refuses a backup that does not match its hash, and refuses to write over existing rows.

## Evidence

| Where | What |
|---|---|
| Local runtime, 5 tests | Every table round-trips; a table of 1,100 rows (more than one page); pruning; a changed backup is refused and nothing is written; a missing backup and a non-empty table are refused |
| Cloudflare, 3 tests | The same on a real R2 bucket and a real D1 database: a backup is written, the database is emptied, the backup is restored, and the audit log comes back entry for entry with its hash chain verifying |

So the acceptance test's second half is met: one restore from a backup into a scratch
database succeeds, on the real platform.

## The restore drill on production's own backups (task 4.1.3, 2026-11-28)

The evidence above used test content. The drill uses a real backup:

    npm run restore:drill                       the latest backup
    npm run restore:drill -- --day 2026-11-28   the backup of one day

It reads production and writes nothing there. It downloads the backup, restores it with
the Worker's own `restore` into a scratch database that exists only in memory, and
checks:

- the file's hash is the one production wrote in its audit log when it made the backup;
- every table restores, and every row read back is the row in the backup;
- the row counts are the ones production recorded;
- the restored audit log's chain verifies, entry for entry;
- the last restored entry is the entry production holds under the same number, so the
  backup is production's and not another database's;
- a second restore over the restored rows is refused, and so is a copy of the backup
  with one character changed.

The downloaded file is deleted before the command ends.

| Backup | Rows | Result |
|---|---|---|
| 2026-11-28 | policy 15, audit log 108, queue 6, switches 1, projects 2 | Passed. Chain verifies, 108 entries |
| 2026-11-26, taken before migration 0007 added two columns | policy 15, audit log 72, queue 5, switches 1, projects 1 | Passed. The new columns came back empty |

Repeat it every quarter and after any migration. Next due by 2027-02-28.

What the drill does not show:

- **It is not a restore into production.** There is still no command that does that. In
  a real loss, the steps are: make a new database, apply the migrations, and run
  `restore` against it from a Worker. Those steps have been done on the test Worker,
  never on production.
- **The scratch database is local SQLite,** not D1. Both are SQLite, and the same
  restore on a real D1 database is covered by the deployed tests, with test content.
- **The hash it trusts comes from the audit log,** which the drill reads from the live
  database. In a real loss the database is gone, and the hash would come from the note
  stored beside the backup in R2. The drill does not read that note.
- **A backup from before a migration restores only while the new columns may be empty.**
  A migration that adds a column which must hold a value would make older backups fail
  to restore. Run the drill after each migration, on a backup from before it.
- **It does not start the Worker on the restored data.** It shows the rows are back and
  the chain holds, not that every screen and store reads them.

## Why seven days

A backup holds the audit log as it was on its day. Text that retention has since removed
(after 7 days), or that an erasure request removed, is still in older backups. Keeping
backups for seven days means removed text can outlive its removal by at most seven days.
A longer keep time gives more recovery and less deletion; this is the owner's to change.

## Limits

- **The first production backup is of empty tables.** The restore proven on the day this
  was written used test content on the test Worker. Since 2026-11-28 production's own
  backups are restored by the drill above.
- **Erasure is not immediate in backups.** A project's deleted logs remain in backups
  for up to seven days. The client notice now says so.
- **The backup is not encrypted by ExecWard.** R2 encrypts at rest. Anyone with access
  to the Cloudflare account can read it, as they can read the database.
- **Same account, same provider.** A backup in R2 survives a damaged or wrongly migrated
  database. It does not survive losing the Cloudflare account.
- **One file, built in memory.** Fine for the sizes expected. A very large audit log
  would need the file written in parts.
- **Restore is a function, not a command.** No tool runs it against production yet.
- **The audit chain proves the restored log is internally consistent,** not that it is
  the latest. A restore from yesterday's backup loses today's entries.
