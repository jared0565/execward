# 2.1.5 Limits on checks and attempts for MCP clients

Date: 2026-11-24. Requirements: FR-47, FR-39, FR-41, Flag 12. Status: **done,** with
one part of the production wiring not yet seen live (see Limits).

## The three parts

| The task asks | How it is met |
|---|---|
| Criteria from `intent` are marked model-supplied | Already true in the core since task 1.7.4: the criteria a call carries are recorded before the run and come back in the report as `source: "model_supplied"`. Now shown over MCP on Cloudflare |
| The run report is returned for display | Every reply carries the whole report: the run's ID, what it called, what it read and wrote, and that nobody independent checked it. Now shown over MCP on Cloudflare |
| A third attempt in a session is refused | New. See below |

## What a "session" is

Over MCP there is none. Each request stands alone, and Cloudflare may serve it from a
different copy of the Worker. So a count kept in memory would reset silently.

**Decision by the project owner, 2026-11-24:** count per signed-in person and project,
in the database, and let it clear itself.

- A run that completes clears the count.
- A run that fails adds one. Two failures in a row may each be followed by another
  try. The third failure in a row closes the project to that caller: later runs are
  refused before they start, and the closure goes to the owner's queue.
- A security failure closes it at once.
- A refusal by a switch the owner threw (Code Mode off, a pause, the kill switch) is
  not counted.
- It reopens when the owner deals with the queue item, when the item runs out of time
  (four hours), or after 30 minutes with no attempt at all. An attempt while closed
  starts the 30 minutes again.

This differs from the in-app rule in one way. There, a failure a retry cannot fix
closes the task at once, because the task is one request from a person. Here there is
no task to close, so such a failure counts as one of the three.

## How it is built

- `src/code-tool/stored-attempts.ts`: the gate. It reads where the caller stands when a
  request arrives and writes how the run ended.
- `migrations/0004_attempts.sql`, `d1AttemptStore`: one small table. A failure is
  added and read back in one statement, so two runs failing at the same moment are
  both counted.
- `src/mcp/adapter.ts`: asks for the gate by the project named in the call.
- `src/mcp/production.ts`: the caller is the signed-in owner; a closure is raised in the
  owner's queue. If the count cannot be read, the run does not start.

## Evidence

- `test/stored-attempts.test.ts`, 12 tests: the limit across separate requests,
  clearing, security closure, the owner's switches not counted, callers and projects
  kept apart, both ways of reopening, runs failing at once, and failing closed.
- `test/mcp-adapter.test.ts`: the count is asked for by project; no run without it.
- `test/deployed/mcp.deployed.ts`, on Cloudflare with the database: three failing calls
  on three separate connections, then a script that would succeed is refused with the
  retry limit named, while another project still runs; a completed run clears the
  count; criteria come back marked model-supplied with the report.

## What the first live run found, 2026-11-24

The project owner tripped the limit on production from Claude Code: one run that timed
out, then three failing runs sent almost together. The limit closed the project and an
item reached the owner's queue, so the production wiring to the queue works. But two
faults showed (audit entries 18 to 25):

1. **A run started after the limit was reached, and ran.** The closure was written to
   the database only after the queue item had been raised, which took about a tenth of
   a second. The third run started inside that gap. Fixed: the closure is written
   first, and the owner is told second.
2. **Two queue items were raised for one closure.** That third run then failed, found
   the project not yet closed, and closed and reported it again. Fixed: closing is one
   database statement that only the first run wins, and only the winner tells the
   owner.

Both are covered by tests that fail on the old code. Neither was caught before because
the test Worker raises no queue item, so the slow step that opened the gap was absent.

## Limits

- **Runs started at the same moment can all run.** The limit is checked when a run
  starts. Several started together each pass the check, and each failure is then
  counted. The project's own limit on runs at once bounds how many that can be.
- **Reopening when the owner resolves the item is not yet seen live.** Raising the
  item was seen on production. Reopening is tested with stand-ins only.
- **The test Worker still raises no queue item,** so a fault in that step shows first
  on production, as it did.
- **One person.** The caller is always the owner today, so "per person" has one value.
  Claude Code and Codex signed in as the owner share a count for a project.
- **The table is not in the backup.** It holds nothing worth restoring: at most a
  count and a refusal that clear themselves.
- **Criteria are still not judged by code.** They are recorded and labelled. Judging
  them is the reviewer's job (tasks 2.2.x).
