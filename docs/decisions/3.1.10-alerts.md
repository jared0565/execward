# 3.1.10 Alerts

Date: 2026-11-28. Status: **built, tested and wired into production. Not seen firing on
production.** Each of the five alerts fires in a test, which is what the task asks for.

## What raises an alert

A run that ends on one of five error codes:

| Event the task names | Error code |
|---|---|
| Policy denial | `policy_denied` |
| Quota hit | `quota_exceeded` (a quota, a spend cap or a per-run limit) |
| Circuit-breaker trip | `circuit_open` |
| Definition change | `definition_changed` |
| Sandbox fault | `sandbox_fault` |

## What an alert is

Every run already produces one metric (docs/decisions/1.9.3-metrics-and-maintenance.md).
The alert reads that metric (`src/metrics/alerts.ts`) and does two things:

1. **A log line, every time.** One line named `execward_alert` in Cloudflare's logs,
   with the kind, the run's ID, the project and what became of the email.
2. **An email to the owner, at most once an hour for each kind.** Fixed words: the kind
   of event and a link to the console. No project, no tool, no run ID and no error text,
   as for every other email (docs/decisions/1.6.7-email.md).

The hourly count is kept in the database's quota counters, so every copy of the Worker
shares it. The hours are clock hours, so two emails of one kind can be a few minutes
apart across the turn of an hour.

An alert cannot fail a run. If the count cannot be kept, the email is not sent: an
email that is not counted could be one of thousands.

## Why a limit on emails

A caller that keeps being refused would otherwise send an email for every run. At ten
runs a minute, the project quota, that is 600 an hour.

## Limits

1. **Not seen on production.** Raising a real alert there means causing a real refusal,
   which also pauses the project until the owner deals with it. So it was not done.
   What is tested: each kind produces the line and the email, with stand-ins for the log,
   the mail and the counter.
2. **It overlaps the queue's emails.** A policy denial, a quota hit and a circuit-breaker
   trip also raise a security exception in the owner's queue, which sends its own urgent
   email within five minutes and a reminder each hour. The owner can get both. The alert
   is the faster one and says which kind.
3. **Only runs raise alerts.** A call turned away before a run starts (no sign-in, an
   unknown tool name at the MCP layer) produces no metric and so no alert. A tool whose
   definition is found changed by anything other than a run is not alerted either.
4. **Two security codes raise none:** `static_check_failed` and `injection_suspected`.
   The task names five events, and these are not among them.
5. **The email says only the kind.** Which project and run is in the log line and the
   console, behind sign-in.
6. **The log is kept for days, not months,** and nothing reads it automatically.
7. **Email must be set up.** Without the email binding and the owner's address the line
   is still logged and no email is sent. Production has both, for the queue's emails.
8. **One email an hour is a first value,** with no measurement behind it.

## What changes now

Production's metric sink now passes through `alertingSink` (`src/mcp/production.ts`).
From this deploy a run that ends on one of the five codes can send the owner an email.
Task 3.1.3 (tier-1 writes) waited on this task and on the paid human review (G.10); it
still waits on the review.
