# Task 0.1.3: executor interface and second implementation path

Decided 2026-11-22. The interface is `src/executor.ts`; `test/executor.contract.test.ts` shows a
caller can run a script knowing nothing but that interface.

## The interface, in one paragraph

The core hands an executor a script, a set of limits and a `SandboxHost`. The host is the only
thing the script can talk to: tool calls, `search()` and `describe()`. The executor returns either
a completed result with captured logs, or a failure with one of five kinds: `script_error`,
`assertion_failed`, `timeout`, `quota_exceeded` or `sandbox_fault`. It holds no policy and no
credentials, and it never runs anything outside the sandbox when the sandbox fails.

## First implementation: Dynamic Workers

Confirmed in task 0.1.2. The script runs in a Dynamic Worker loaded with `globalOutbound: null`
and no `env` except one custom binding that carries `SandboxHost` calls back to the broker.
CPU time uses the platform's `cpuMs` limit; wall-clock time and the host-call count are enforced
by the executor in the host Worker.

## Second path: Cloudflare Sandbox SDK (containers)

Checked against Cloudflare's docs on 2026-11-22. Not built; this records that it would fit
behind the same interface.

| Need | How the container path meets it | Source |
|---|---|---|
| Isolation | "Each sandbox runs in a separate VM", with separate filesystem, processes and network stack. | [Sandbox security model](https://developers.cloudflare.com/sandbox/sdk/concepts/security/) |
| No network | "A Container starts with `enableInternet: false` by default, so it cannot reach the Internet." | [Sandbox security](https://developers.cloudflare.com/sandbox/concepts/security/) |
| Reaching the broker | Only requests that an outbound handler in the Worker intercepts leave the container, so `SandboxHost` calls travel as HTTP to one intercepted hostname. | Same page |
| Credentials stay out | The outbound handler runs in the Worker: "The sandbox never sees the real credential." | [Sandbox security model](https://developers.cloudflare.com/sandbox/sdk/concepts/security/) |
| Limits | "CPU, memory, and disk quotas are enforced per sandbox." | Same page |
| Running the script | The container runs any language, so the JavaScript runs under Node inside it. | [Sandbox SDK 1.0](https://developers.cloudflare.com/changelog/post/2026-09-30-sandbox-sdk-1-0/) |

**Why it is the fallback and not the first choice.** It is a different isolation boundary (a VM,
not a V8 isolate), which is the point of a second path: a V8 escape bug would not carry over.
The costs are a slower start than an isolate and a heavier runtime. Its start time and price per
run were not looked up; they matter only if the switch is ever made.

**What the interface had to avoid to keep this possible.** `SandboxHost` is plain async methods
with JSON-serialisable arguments and results. It does not expose Workers RPC stubs, bindings or
any Dynamic Worker type, because the container path can only speak HTTP to the broker.

## Not chosen as the second path

gVisor and Firecracker, from the PRD's sandbox table, would mean running and patching the
sandbox ourselves. The PRD's risk table already rules that out for a single builder: "Use the
platform's sandbox instead of building one."
