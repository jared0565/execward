# 2.1.3 A tool list that does not change

Date: 2026-11-24. Requirement: FR-14. Status: **done.**

## What is required

A model client reads the server's tool list at the start of a session and may cache
it. If the list changed as a session discovered tools, the client's cache would go
stale, and a server could show a model one set of tools at approval time and another
later. So the list must stay the same however many tools a session finds.

## How it is met

The MCP server offers exactly one tool, `code`. Every upstream tool is found from
inside a script, through `search()` and `describe()`, and called there. Nothing a
session discovers is ever added to the list.

Since task 2.1.9, a client whose model header names Claude Haiku is also listed up to
four looking-around tools beside `code`. That list is fixed by the client's
configuration and the policy table, not by what a session finds, so it is as stable.

## What the test found

The list itself was already fixed. But the MCP library, by default, tells every client
that the list **may** change (`tools.listChanged: true`). That is a promise ExecWard
does not want to make: a client told so is entitled to re-read the list, and expects
change notices. The adapter now states `listChanged: false`.

## Evidence

- `test/mcp-adapter.test.ts`: the list is byte-for-byte the same before and after
  calls, the same for a second client, and the server says it will not change.
- `test/deployed/mcp.deployed.ts`, on Cloudflare with the real service: one session
  searches for a tool, reads its types, calls it, and reads the list after each step.
  The list is the one tool, word for word, throughout.

## Limits

- **The Code Mode switch is a separate matter.** With Code Mode off the tool stays
  listed and a call is refused with `code_mode_off`, and a client is told of a change
  on its next call (both decided in task 2.1.4).
- **A new release can change the list,** for example by rewording the tool's
  description. Stability is within a deployed version.
- **One test run on Cloudflare failed in three unrelated tests** (two on backups, one
  on switch changes made at the same moment) and passed on the next run with no
  change to them. The cause was not found.
