# 1.3.1 and 1.3.2 The policy table and the broker's caller rules

Date: 2026-11-23. Requirements: FR-50, FR-32, FR-6, FR-13, FR-41, the policy record
contract. Threat-table rows on policy bypass and probing. Status: **1.3.1 is done on a
local database. 1.3.2 is done except for hook-guarded tools.** Nothing is deployed; the
real D1 database needs a Cloudflare account.

## What it does

**The policy table** (`src/broker/policy-store.ts`, `migrations/0001_policy.sql`) holds
one record per wrapped tool, in D1.

**The broker** (`src/broker/broker.ts`) is the host side of every call a script makes. It
is built fresh for each run. A call reaches a wrapped tool only if the tool has a record,
the record lets scripts call it, and it is tier 0.

| The script calls | Result |
|---|---|
| A tool with no record | Refused |
| A direct-only tool | Refused |
| A tier-1 or tier-2 tool | Refused, until the dry run and approvals exist |
| Any tool while the policy table cannot be read | Refused |
| A tier-0 tool a script may call | Forwarded |

## Choices

- **Default deny is absence.** A tool with no record is treated as the highest data
  class, tier 2 and direct-only. There is no "allow" default to forget to change.
- **A bad stored record is an error, never a guess.** A row that is not JSON, does not
  match the contract, has an unknown field, or is filed under another tool's name makes
  the store throw, and the broker refuses the call. It is never tidied into something
  more permissive.
- **Fail closed.** If the table cannot be read, or does not exist, every call is refused.
  A missing table is not an empty policy. The store's own error text is not shown to the
  script.
- **A refusal ends the run (FR-41).** After the first refusal, every later call in that
  run is refused too, and the run is reported as `policy_denied` even if the script
  caught the error and returned a value. The script's result and logs are not returned.
  A script cannot map the policy by trying things and catching the errors.
- **Search and describe show only what a script could call.** Asking about a name is not
  treated as an attempt to use it, so `describe` of a hidden tool is an ordinary error.
- **The refusal names the tool, never the arguments.**

## Evidence

- 14 tests on the store and broker in memory.
- 7 tests on the policy table in a local D1 database, inside the local Workers runtime.
- 5 tests of the whole stack together in the local runtime: code tool, static check,
  Dynamic Worker, broker and D1. A script that calls a direct-only tool, catches the
  error and carries on gets `policy_denied`, and exactly one upstream call was made.

## Limits

- **Hook-guarded tools are not handled.** Task 1.3.2 says a hook-guarded tool called from
  a script is refused. The policy record has no field for that yet, so 1.3.2 stays open.
- **The policy is one table for all projects.** The record contract has no project field.
  Per-project rules come with data classes (task 1.3.7).
- **Arguments are not checked yet** (task 1.3.3), results are not tagged (1.3.4), and
  there are no quotas (1.3.8). Refusals are kept in memory for the run; the audit log is
  task 1.4.1.
- **No real tool is wrapped.** The upstream is a stand-in in every test. The MCP client is
  a later task.
- **Local D1 only.** Production configuration has no database binding yet, because a real
  one needs an account.
- **Tier 1 and 2 are refused outright**, which is stricter than the final design. It
  loosens only when the dry run and approvals are built.
