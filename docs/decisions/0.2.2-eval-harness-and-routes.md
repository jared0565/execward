## What a cheap model can and cannot tell us

- Token saving is set mostly by the size of tool definitions and tool results, so a small
  model measures it as well as a large one. This is reasoning, not yet a measurement.
- Success depends on the model. A small model can show a drop on the code-tool arm that a
  larger model would not. So a pass on the cheap pair is good evidence, and a fail is
  inconclusive: the failing tasks are then re-run one tier up before any conclusion.

## How the routes work

- `src/eval/providers/openrouter.ts`: Chat Completions through the OpenAI SDK with
  OpenRouter's base URL. Each request names one upstream host (`anthropic` or `openai`)
  with `allow_fallbacks: false` and `data_collection: "deny"`, so a run measures one model
  served one way. The assistant message is replayed unchanged, reasoning details included.
- `src/eval/providers/anthropic.ts`: Messages API, as before.
- `src/eval/providers/openai.ts`: Responses API, stateless (`store: false`), replaying every
  output item in order, reasoning items included.
- `src/eval/routes.ts`: `runWithFallback` tries the routes in order. It moves to the next
  route only on `provider_error`. A refusal, a cut-off or a malformed tool call is the new
  failure cause `model_stopped`: that is a result about the model, so it is not retried
  elsewhere. A run never changes route part-way, because each route keeps the conversation
  in its own form. Every attempt is reported, failed routes included.
- `src/eval/preflight.ts`: `assertKeysPresent` stops a run before any call and names the
  missing variables, never their values. `scripts/eval-one.ts` requires all three keys.

A fallback changes how the model is reached, so the route is on every run record
(`provider`). The baseline report must show how many runs used each route.

## The real run

`npx tsx scripts/eval-one.ts --each-route`, 2026-11-22, one task ("How many open issues do
the repositories alpha and beta have in total?", two tool calls needed, answer 42).

| Model | Route | Correct | Turns | Input tokens | Output tokens | Cost |
|---|---|---|---|---|---|---|
| Claude Haiku 5.5 | OpenRouter | yes | 2 | 1,057 | 125 | $0.000168 reported |
| Claude Haiku 5.5 | Anthropic | yes | 2 | 1,057 | 125 | $0.000168 estimated |
| GPT-6 Luna | OpenRouter | yes | 2 | 278 | 71 | $0.000063 reported |
| GPT-6 Luna | OpenAI | yes | 2 | 278 | 73 | $0.000064 estimated |

Total about $0.0005. What this shows:

- Both routes report the same token counts for the same model, so a fallback does not
  distort the measurement on this task.
- The cost OpenRouter reports equals tokens times the listed price, so its `cost` field is
  in US dollars and the prices are passed through.
- Claude counted 1,057 input tokens where GPT counted 278 for the same prompt and tool.
  The difference is each provider's own overhead for offering tools. Token counts are
  therefore compared within a model across arms, never between the two models.

Before the paid run, the runner was started with two keys absent from the process. It
stopped with "Cannot start: ANTHROPIC_API_KEY, OPENAI_API_KEY are not set. No model call
was made." and exit code 1.

## Limits

- One trivial task proves the plumbing, not the estimate. The cost per run for real tasks
  is known only after the first pass of the task suite (0.2.3, 0.2.5).
- `inputTokens` is taken as the provider's full input count. Neither OpenRouter's nor
  OpenAI's page states outright that cached tokens are inside it; no caching was used here.
- OpenRouter is a further processor of whatever the eval sends. The eval sends fixture data
  only. This belongs in the DPIA (G.11) before any real data is evaluated.
- The keys live in the Windows user environment. A session started before they were set
  does not see them, and the launch command has to copy them into the process.
