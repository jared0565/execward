# 1.9.4 The latency the core adds

Date: 2026-11-23. Requirement: NFR performance. Budget (task 0.2.6): 10% of run time or
0.5 seconds per run, whichever is larger. Status: **measured on Cloudflare with every
store on the database, as production will run. Within the budget for scripts of up to
about 40 tool calls; at its edge for 50.**

## Result

Measured on the deployed test Worker with `npm run measure:latency`: 40 samples of each
case, one at a time, timed from the owner's machine, after two warm-up requests. "Added"
is a case's median less the baseline's.

| Case | Median | 95th percentile | Added |
|---|---|---|---|
| Baseline: a request refused at the test Worker's gate | 31 ms | 101 ms | — |
| Sandbox and checks only, no tool call | 31 ms | 61 ms | 0 ms |
| Sandbox and checks only, 50 tool calls | 37 ms | 61 ms | 6 ms |
| Broker and policy, stores in memory, 10 tool calls | 38 ms | 58 ms | 7 ms |
| **On the database, no tool call** | 273 ms | 312 ms | **242 ms** |
| **On the database, 1 tool call** | 318 ms | 356 ms | **287 ms** |
| **On the database, 10 tool calls** | 440 ms | 542 ms | **409 ms** |
| **On the database, 50 tool calls** | 554 ms | 620 ms | **523 ms** |

"On the database" is `src/service.ts`, the one function a served route must go through,
with the policy table, project classes, switches, quota counters and audit log all on D1.

**The database is nearly all of it.** The sandbox, the static check and the broker's own
work add under 10 ms. Each round trip to the database costs about 18 ms, and they
happen one after another.

## What it took to get there

The first measurement on the database was far over the budget.

| Version | No call | 10 calls | 50 calls |
|---|---|---|---|
| As built: switches, policy and a counter read or written on every call | 227 ms | 803 ms | 3,039 ms |
| Calls counted ahead in blocks | 312 ms | 827 ms | 2,466 ms |
| And the switches and policy re-read at most every 0.25 s within a run | 242 ms | 409 ms | 523 ms |

Rows were measured at different times, and the noise between runs is tens of
milliseconds: compare the shape, not the last digits.

1. **Calls are counted ahead** (`src/broker/broker.ts`, `src/broker/quotas.ts`). A daily
   limit is counted in blocks of 1, 2, 4, up to 16 calls, so a loop writes a counter
   about once in 16 calls. A block the limit has no room for is not kept, and the call
   is counted singly, so a limit is still met exactly. What was counted and not used is
   given back when the run closes.
2. **The switches and each tool's policy are re-read at most every 0.25 s within a run**
   (`RUN_RECHECK_MS` in `src/service.ts`). **This changes how fast a switch acts, and
   the project owner chose it on 2026-11-23.** Before, a kill, a pause or a policy
   change stopped a running script at its very next tool call. Now it stops it within a
   quarter of a second. A new run always reads afresh.

   A correction: the owner was asked this as a choice between two of the PRD's
   requirements. That was wrong. FR-17 says a switch thrown mid-run ends the script; it
   never said "at the next call". The every-call check was the implementation's own
   choice, stated in a code comment and repeated without reading the PRD. The trade
   was between the latency budget and that stricter implementation. The PRD now states
   the quarter second (revision 204).

Tried and taken out: reading the switches and the policy at the same time. It gained
nothing measurable. The database answers one query at a time.

## What is left

- **The fixed cost of a run is about 240 ms**, roughly 13 round trips: the switches,
  six for admission (four counters and a slot), the project's class, two writes to the
  audit log at two round trips each, and the slot's release. It could be roughly halved
  by sending admission as one batch and by not re-reading the head of the audit log.
  Not done: it is inside the budget, and both touch code that guards money and the log.
- **Each further tool call costs about 6 ms** when calls come quickly, more when they
  are spread out, since a reading older than 0.25 s is taken again.

## How to read it

- The tool in these runs answers at once. A real tool's own time is not ExecWard's.
- The budget's other half is 10% of run time. A Code Mode task took a median of 4.3 to
  6.2 s in the eval (task 1.9.5), so 10% is 0.4 to 0.6 s. The 50-call figure sits at
  that line.

## Limits

- **One place, one time.** One machine to the nearest Cloudflare location, one evening,
  warm isolates, an almost empty database. A cold start is not counted. A full audit
  log or a database in another region would be slower.
- **Not a load test.** Requests were sent one at a time. Two runs at once write the same
  audit log and wait on each other.
- **The test Worker, not production.** Production served no route when this was
  measured. It now serves the same function at `mcp.execward.com`; that has not been
  timed.
- **Timed runs were spread over 60 test projects**, because one project may start only
  10 runs a minute. That limit refused the first attempt at measuring, which is the
  limit working on the real database.
