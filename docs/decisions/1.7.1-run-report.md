# 1.7.1 The run report

Date: 2026-11-23. Requirement: FR-39. Status: **done and tested in memory.**

## What the report is

A factual record the server builds itself and returns beside every reply, whatever the
outcome: completed, error or refused. The model's own account of a run is never the
source of truth; this is.

| Field | What it holds today |
|---|---|
| Calls by tool | Every call asked for, counted when asked, so refused and failed calls count |
| Records read | Counted by the broker from tool results |
| Records written | Always 0: only read-only tools exist |
| Errors | The error that ended the run, then every failed call the script survived |
| Retries | Always 0 until task 1.7.3 |
| Assertions | Passed and failed counts from the sandbox |
| Side effects | Always empty: only read-only tools exist |
| Verification | Always `not_applicable` until task 1.7.4 |
| Run ID, script hash, duration | As in the audit log |

Most of this was built with the `code` tool (task 1.2.4). This task closed three gaps.

## The three gaps

1. **A script could hide a failed call.** If a script caught a tool's error and carried
   on, the report listed no error. Now every failed call is listed, with its error code
   and the tool's name. The error's own words are left out because they can hold data
   from the upstream. At most 20 are listed, with a count of the rest.
2. **The log and the reply could disagree.** The report is now written to the audit log
   exactly as returned, for runs and for refusals.
3. **A failed call's name could carry data out.** See below.

## A leak found and closed

Found while writing this task's tests, in work already merged (task 1.3.6).

A script chooses the name of the tool it calls. A script that had read data it was not
allowed to return could call a made-up tool whose name was that data. The call was
refused, but the name came back to the model in two places: the refusal message and the
report's calls-by-tool list. Output hygiene withheld the result and let the name through.

Closed in both places:

- **The refusal message names a tool only if the policy table has a record for it.**
  Anything else is "a call was refused". The owner's log keeps the real path.
- **When content is being withheld, the report names only tools that answered at least
  once in the run.** Other calls are counted under "(a call that did not succeed)".

Cost: in a run where content is withheld, a real tool that was refused and never
answered is not named in the calls-by-tool list. Its name is still in the refusal message.

## Limits

- **Records read is the broker's count** of items in tool results, not a count of what
  the script actually used.
- **A run cut off by a timeout** reports calls still in flight as calls, not as errors.
- **The same class of leak may exist elsewhere.** Anything a script chooses that is
  echoed back is a candidate. Checked here: tool paths in the report and in refusal
  messages. Not yet checked: the line text added to a failed assertion's message when
  nothing is withheld, and the wording of schema errors, which a script sees inside the
  sandbox but which are not returned in the report.
- **The report is not yet shown to anyone.** Displaying it, and reconciling a model's
  summary against it, are tasks 1.7.2 and 1.9.2.
