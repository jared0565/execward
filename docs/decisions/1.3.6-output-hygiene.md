# 1.3.6 Output hygiene

Date: 2026-11-23. Requirement: FR-36: "mark the final value as untrusted tool output, mask
fields above the run's allowed class, return counts or sample rows with totals, and encode
output for its destination." Status: **done and tested, in the form the per-run data label
allows.** Two parts differ from the PRD's wording; both are set out under "Where this
differs".

## What it does

| FR-36 asks for | What is built |
|---|---|
| Mark the final value as untrusted | Every completed and error reply carries `untrusted: true` and the data class the run read |
| Mask what is above the allowed class | If the run read data above the project's class, the result, the logs and the script's own error text are all withheld, and the reply says why |
| Counts with totals | The run report counts the records read (a list by its length, anything else as one) beside the calls per tool |
| Encode output for its destination | `presentForModel` hands a reply to a model as JSON inside one marked block, escaped so that nothing in it can close the block or pose as instructions |

## Where this differs from the PRD

1. **Whole replies are withheld, not single fields.** The owner chose one data label per
   run (2026-11-23), kept outside the script. So ExecWard knows a run read confidential
   data; it does not know which part of the returned value came from it. A script that
   read a confidential file and returns the number 42 has that 42 withheld, because 42
   could be anything, including an encoding of the file. This is safe and blunt.
2. **Sample rows are not returned.** FR-36 says "counts or sample rows". Counts are
   returned. Samples would mean ExecWard choosing rows of tool data to show the model
   outside the script's control, which works against the masking above.

## Choices

- **A project may return only public data unless told otherwise.** The allowed class is
  supplied per project (task 1.3.7 will set it); left out, it is the most cautious one.
- **A host that cannot say what was read is treated as having read the highest class.**
- **A script's own words are withheld with its result.** A script decides what it throws,
  asserts and logs, so all three could carry the data. ExecWard's own messages (a timeout,
  for example) are kept.
- **A masked reply still reports what happened:** calls per tool, records read and the
  data class. The model learns that the run worked and why it got nothing back.
- **A run that read nothing is never masked.** Pure calculation has no data class.
- **Escaping, not stripping.** For a model, every `<`, `>` and `&` in the JSON is written
  as a JSON escape. The value is unchanged when read back, but it cannot contain a tag.
- **Contract version 1.4.0:** optional `untrusted`, `dataClass` and `masked` on replies.

## Evidence

13 tests: the marking, record counts, masking in each case above (including a script that
returns a harmless-looking value, and one that puts the data in an error message), the
cautious defaults, and a reply whose content tries to close the block and issue
instructions.

## Limits

- **Marking is a signal, not a control.** A model can still be persuaded by text inside
  the block. The marking makes the boundary clear; it does not make the model obey it.
- **The MCP adapter hands every reply to the client through `presentForModel`**
  (`src/mcp/adapter.ts`, task 2.1.1), as do the test app and the eval's code arm.
- **Masking will be felt.** With GitHub source files classed as confidential, a project
  allowed only internal data gets nothing back from any run that opens a file. That is
  the intended effect of the class, and the place to adjust is the project's class
  (1.3.7), not this rule.
- **The record count is approximate.** A tool that returns `{ items: [...] }` counts as
  one record.
- **Content is not scanned for injection patterns here.** FR-36 does not ask for it;
  `injection_suspected` belongs to a later task.
