# 1.1.5 First deployment and the rollback drill

Date: 2026-11-23. Requirement: NFR recovery. Status: **done, by hand, once.**

## What was done

The project owner approved deploying into their existing Cloudflare account. Then:

1. `wrangler deploy` from `main` at `7f6f4f2`. Version `3c6ca333`. The Worker is the
   health-check scaffold, with one binding (the Worker Loader) and no public address.
2. `wrangler deploy` again, tagged `rollback-drill`. Version `4c1f87fa` took all traffic.
3. `wrangler rollback 3c6ca333-0627-4fb9-938c-4d10197c9391`. Cloudflare reported that
   version back at 100% of traffic, and `wrangler deployments status` agreed.

Every deploy is a numbered version on Cloudflare. A rollback is one command and names
the version to return to.

## Limits

- **Both versions held the same code.** The drill shows the mechanism works. It does not
  show a behaviour change being undone, because the Worker has no address to call.
- **A rollback restores code and configuration only.** It does not undo a database
  migration. A release that changes a table needs its own way back.
- **Done by hand.** No workflow deploys or rolls back. CI would need a Cloudflare
  credential in the repository's secrets, which is the owner's step.
- **Whether the account is on Workers Paid is not proven by this.** The upload accepted
  the Worker Loader binding. Running a script in it on Cloudflare is the real test, and
  that is task 1.2.2.
