# 1.9.6 Does the tool description work for both model families?

Date: 2026-11-23. Requirement: model portability. Status: **GPT-6 Luna passes. Claude
Haiku 5.5 passes every task but one, and two attempts to fix that one did not work. A
decision is needed from the project owner.**

## Where it stands

From the final run of task 1.9.5 (`docs/research/1.9.5-code-arm-report.md`), 30 tasks,
five runs each:

| | Claude Haiku 5.5 | GPT-6 Luna |
|---|---|---|
| Tasks passed in at least one run | 29 of 30 | 30 of 30 |
| Runs correct | 145 of 150 | 150 of 150 |
| Bounded tool-heavy tasks | 100 of 100 | 100 of 100 |
| Typings: scripts refused for wrong arguments | 19 of 433, each corrected on the next try | 0 of 530 |

The same description and the same typings are given to both. Neither family needed
its own wording.

## The one failure

`rollback-command` asks how to roll back a deploy. The answer is one line in
`docs/deploy.md` in the invented repository. Finding it takes three steps: list the
files, see `docs/`, read the file.

- With direct tool calls Claude Haiku passes 4 of 5, using about six tool calls.
- With the code tool it passes 0 of 5. It lists the tools, sees none named for deploys,
  and says it cannot tell. Pushed to look, it writes one script that reads a file or two
  it guessed (`README.md`, `DEPLOY.md`), finds nothing, and stops.
- GPT-6 Luna passes 5 of 5 either way.

So the model gives up sooner when each step of looking costs a script. It is not a
fault in discovery or typings.

## What was tried, and reverted

Each on 15 runs per model (three tasks, five runs), about 5 cents each.

| Change | Result on Claude | Kept |
|---|---|---|
| `search()` returns a line on what each tool does, not only its name | 1 of 5 on the task, and another task fell from 5 to 3 | No |
| The description says a missing tool name is not an answer, call tools and look | 0 of 5. It now calls tools, once, then stops. More tokens used | No |

Neither is in the code. What is deployed and on `main` is what run 3 measured.

## Limits

- Fifteen runs are few. They can show a change did not fix the task. They cannot show
  it did no harm elsewhere.
- One small model per family. A larger Claude model was not run and may well persist.
- The task is of the exploratory type. Code Mode's target is bounded tool-heavy work,
  and the token target covers only that type. The success target covers every task.

## Decided, 2026-11-24

The project owner chose to accept this with a guard. Code Mode is aimed at bounded
tool-heavy work, where both models pass 100 of 100. Exploratory tasks stay on direct
tool calls for Claude Haiku. The guard is a written rule today; nothing in the code
applies it yet, and task 2.1.9 does. The target in 0.2.6 stands for every other task
and model. What follows is the question as it was put.

## The decision

The target set in task 0.2.6 allows no task that passes with direct calls and fails
every run with the code tool. One does, on one model. Gate 1 (task 1.9.8) cannot pass
as the target is written.

**The project owner chose, on 2026-11-23, to decide this at Gate 1**, with all the
evidence in one place. The options then: test a larger Claude model (about $3), narrow
the rule to bounded tool-heavy tasks, or keep the target and keep working on the task.
Until then this task stays in progress.

Paid runs for this task: about 11 cents. Total against the $5 approved for the eval:
$1.66.
