# Task 2.3.2: whether to ship a skill. A trial first

Date: 2026-11-26. Traces to: the PRD's Open questions and Delivery options.
Status: **open. Waiting on usage from a trial.**

## The question

The PRD's proposed decision is the core plus two adapters, "with the skill added later
if usage data shows models ignore the tool". Its open question reads: "Should the skill
ship at all, or is the tool description enough? Decide from Phase 2 usage data."

## Why it cannot be decided today

On 2026-11-26 production held 2 metered runs. Both were the project owner's own live
checks, made with a prompt that told the model to call the tool. They say nothing about
whether a model chooses the tool unprompted.

## The owner's decision, 2026-11-26

Try ExecWard in another repository of the owner's own, and decide from that.

- **Not this repository.** Sessions here have the files on disk and the `gh` command,
  so they seldom need ExecWard's GitHub reads, and they build the tool, so they already
  know it. Low use here would not show that the description failed.
- **The trial repository is the owner's own website, `Bytes-Web`.** It is not a client's.
  Client data stays out until the gates for it are cleared (G.7, G.10).

## What was set up

- Production now has a project `bytes-web` at level `internal`, added with
  `npm run setup:github -- --yes --project bytes-web --class internal` (audit entry 74).
  Read back afterwards: two projects, 15 policy records.
- At `internal`, 7 of the 15 GitHub tools are listed. The 8 that return confidential
  data, file contents among them, are not. So the trial covers issues, pull requests,
  branches and repository details, not reading code.

Still the owner's to do: check the GitHub App is installed on the trial repository,
and add the MCP server to Claude Code there.

## Things that weaken the trial, known before it starts

- **The model must be told the project's name.** The `code` tool takes the project as an
  argument from the model. A project ExecWard has no record of is refused (since the
  second sandbox review, the same day; before it, such a call ran as `public`). So
  sessions in the trial repository need one line telling them the name. That line is a small nudge towards the tool, and a skill is a larger
  one. The line should name the project and say nothing about when to use the tool.
- **ExecWard cannot see a call that was never made.** It counts runs. Whether a model
  read GitHub another way instead (the `gh` command, another GitHub server) can only be
  counted on the client's side.
- **Sessions there also have `gh`.** A model that prefers it is not wrong to.
- **One repository, one owner, one client (Claude Code).** Enough to show a clear
  pattern, not to measure a rate.

## How the decision will be made (proposed, not yet agreed with the owner)

- The trial runs until about 10 sessions in the trial repository have needed GitHub
  data, or two weeks, whichever comes first.
- Counted on ExecWard's side: runs for the project `bytes-web`, from the stats report.
- Counted on the client's side: sessions that read GitHub by another route.
- If the model reaches for the tool in most of those sessions, the description is
  enough and no skill is built. If it mostly goes round the tool, a skill is built and
  the trial repeated with it. In between, the owner decides.
