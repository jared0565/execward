# 1.6.1 How the owner signs in to the console

Date: 2026-11-23, updated 2026-11-24. Requirements: FR-49, FR-27, FR-16, FR-52.
Status: **working. The owner signed in at `console.execward.com` on 2026-11-24, with
an email code and an authenticator app, and the console page loaded. A request that
has not signed in is sent to Cloudflare's sign-in page. The owner then set and cleared
the kill switch and recorded onboarding, and all three changes were read back from the
production database.**

## The decision

The project owner chose **Cloudflare Access** on 2026-11-23, over building passkey
sign-in in ExecWard and over leaving the console until after Gate 1.

Access sits in front of the Worker. It signs the person in and asks for a second
factor. For a request it has authenticated, the platform hands the Worker the signed-in
identity (`ctx.access`). ExecWard holds no password, no passkey and no session of its
own.

Read in Cloudflare's documentation on 2026-11-23:

- Access can guard a Worker on its `workers.dev` address or on a hostname of a domain
  on the account. The console uses the second.
- Access can ask for its own second factor on one application: an authenticator app, a
  security key, or the device's fingerprint or face check ("independent MFA").
- `ctx.access` is absent when Access did not authenticate the request.
- `ctx.access` is not passed to a Worker that uses Static Assets. The console page is
  therefore served by the Worker's own code.

Not confirmed: that Access stays free for one user. The documentation search did not
return the plan limits. Zero Trust already existed on the account, so no plan was
chosen during setup and no price was shown. Nothing is to be paid for without the
owner's say.

## What ExecWard checks on every console request

`src/console/access.ts` turns `ctx.access` into a principal. The owner is the owner
only when all of these hold:

1. Access authenticated the request.
2. The audience tag is this console's Access application (`ACCESS_AUD`).
3. The identity can be read, and is a person, not a service token.
4. The email is the owner's (`OWNER_EMAIL`).

Then the existing gate applies (`requireOwner`): the sign-in must be no more than 12
hours old, taken from the identity's sign-in time.

Anything else is anonymous and is refused: a missing setting, an identity that cannot be
read, another person, a sign-in to a different Access application. **Nothing in the
request itself is read to decide who is asking**: not a header, a cookie or the body. A
test sends forged Access headers and is refused.

`ACCESS_AUD` and `OWNER_EMAIL` are stored as Worker secrets. Neither is a credential
for anything. They are secrets so that the owner's address is in no file, no log and
not in this public repository. They are the only secrets the deployed check allows
(`ALLOWED_SECRETS`).

The audit log names the owner by Access's user id, not by email address.

## What the console does

One page at `/console`, with the state at `/console/state` and changes at
`/console/action`. It covers the kill switch, Code Mode, onboarding (the governance
profile; other fields keep their safe defaults), pausing a project, blocking a tool,
and the escalation queue (`/console/queue`).
The switches are now kept in the database, not in memory.

For the browser:

- **A change must come from the console's own page.** It must carry the page's origin,
  a header only the page sends, and be JSON. A form on another site cannot send that.
- **The page loads nothing from anywhere else.** Its content policy allows one script
  and one style block, each named by a random value made for that response. No inline
  handlers, no outside files, no framing.
- **Everything shown is written as text,** so a project or tool name cannot become
  part of the page.
- **Who is asking is settled before the request is read.** A refusal says nothing
  about what was sent.
- **ExecWard's own failures are not shown.** The browser gets a fixed sentence.

Evidence: `test/console-http.test.ts`, 59 tests, with the 27 in `test/console.test.ts`
for the actions underneath.

## Limits

- **ExecWard cannot see that the second factor was asked for.** Requiring it is a
  setting on the Access application, and Access enforces it. If that setting were
  removed, ExecWard would accept a sign-in without it. The deployed check does not read
  Access's settings yet.
- **Whoever controls the Cloudflare account controls the console.** They could change
  the Access policy or the two secrets. This was already true of everything the Worker
  does; the account's own sign-in protection matters as much as the console's.
- **Three actions have been tried on the live console** (2026-11-24): set the kill
  switch, clear it with a reason, record onboarding. Read back from the production
  database: the switches at version 3, kill switch off, Code Mode off, the formal
  profile recorded; and three audit log entries, numbered 1 to 3, each naming the owner
  by Access's user id, with no email address in any of them. Not tried there: the Code
  Mode switch, pausing a project, blocking a tool, and the queue.
- **The sign-in page is headed with another project's name.** Zero Trust is shared by
  the account and was named when it was first switched on. Renaming it is the owner's
  call, since it shows on every project's sign-in page.
- **One second factor is enrolled.** If the owner loses it, it has to be removed from
  the Cloudflare side before another can be enrolled.
- **A sign-in lasts up to 12 hours here,** or less if Access's own session is set
  shorter. A stolen, unlocked browser inside that time can use the console.
- **Onboarding through the page records the profile only.** Approvers, approved
  providers, project data classes, meter level and the outbound allowlist cannot be set
  from the page yet.
- **The escalation queue's page** was added on 2026-11-24 (see
  1.6-escalation-queue.md). "Keep paused" leaves an item in the queue on purpose.
- **No email.** The owner chose on 2026-11-23 to wait for the domain and use
  Cloudflare's email sending. Until then urgent items show only in the console.

## What was set up on Cloudflare, 2026-11-24

The owner said the domain `execward.com` was already on the Cloudflare account, chose
`console.execward.com` for the console, and asked for the setup to be done for them.
Checked first-hand that day: the domain is active on the account; Zero Trust already
existed there, made for another project, with no Access applications and with the
second factor switched off.

Done, in this order, so the Worker was never reachable without Access in front:

1. **The second factor was allowed on the account**: authenticator app, security key or
   device biometrics. It was not made a requirement for every application, because
   other projects share the account. The account's other settings read back unchanged.
2. **An Access application for `console.execward.com`** was created: second factor
   required, sign-in by one-time code to email, a 12-hour session, a cookie that scripts
   cannot read and other sites cannot send. Its one policy admits a single address,
   which is a placeholder that nobody holds.
3. **`ACCESS_AUD` was stored** as a secret on the Worker.
4. **The Worker was given the address**, as its only route (`ALLOWED_ROUTES`). It still
   has no `workers.dev` address: Access guards a hostname, and a second address would
   be a way in that Access does not guard. The configuration check refuses any other
   route.

5. **The owner gave their sign-in address.** It is in the Access policy and in the
   `OWNER_EMAIL` secret, and in no file.
6. **The owner signed in.** Two things had to be put right first, both mistakes in the
   setup rather than in the code:
   - **The App Launcher was not switched on.** Access enrols a second factor through
     its App Launcher page, so without it "Set up MFA" led to a dead end. The
     documentation mentions the App Launcher only as exempt from the second factor,
     and that was not read as "required". It is now on, for the owner's address only,
     guarded by the email code alone (it cannot ask for a second factor, being where
     one is enrolled).
   - **The sign-in cookie was set to "strict".** A strict cookie is not sent on a visit
     that began on another site, and sign-in arrives from Cloudflare's sign-in site, so
     the browser looped. It is now "lax": still unreadable by scripts, still not sent
     with a form posted from another site. The console's own check that a change comes
     from its own page does not depend on it.

Evidence of the sign-in: the owner's report of the console page, showing version 0 and
every switch in its starting position; and Access showing "No authentication methods
set up" before a second factor was enrolled, which is Access refusing to go on without
one. Checked from outside the same day: the page, the state and an action each answer
with a redirect to the sign-in page, including a request carrying forged identity
headers.

## What the setup rests on that this repository does not check

- The Access application and its policy live in the Cloudflare account. If the
  application were deleted, the hostname would be open to the internet; the console
  would still refuse everyone, because without Access there is no identity, but the
  health check would be public. `npm run check:deployed` does not read Access's
  settings yet.
- The second factor being required is a setting on that application.
- The health check at this address now sits behind Access too.
