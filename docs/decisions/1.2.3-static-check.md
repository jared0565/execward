# 1.2.3 The check on a script before it runs

Date: 2026-11-22. Requirement: FR-33. Threat-table rows 4 (sandbox escape) and 14 (secrets
in logs). Status: **built, tested and, since task 1.2.4, in the run path.** Recording the script hash in the audit log is task
1.4.1.

## What it does

`checkScript(script)` in `src/static-check/check.ts` returns either "ok" or a
`static_check_failed` error, and in both cases the SHA-256 of the script. It refuses a
script that:

| Rule | Refuses |
|---|---|
| Size | More than 64 KB, counted in bytes, before any parsing |
| Syntax | Anything that is not valid JavaScript (2024 edition), with the line |
| Secrets | A literal with the shape of a GitHub, AWS, Anthropic, OpenAI-style, Slack, Stripe or Google key, a signed web token, or a private key. The matched text is never repeated in the error |
| Blocked constructs | `eval`, the `Function` constructor, dynamic `import()`, `WebAssembly`, `import` and `export` statements, `import.meta`, and reading `.constructor` (the usual route to the Function constructor) |
| Globals | Any global that is not part of the Sandbox API or the allowed language built-ins: `fetch`, `process`, `globalThis`, `require`, `setTimeout`, `Reflect`, `Proxy`, `crypto` and everything else |
| Reassignment | Assigning to `tools`, `JSON` or any other allowed global |

## Choices

- **Default deny on globals.** The check does not list dangerous names. It lists the
  allowed ones and refuses the rest, so a global nobody thought of is refused too.
- **Real scope analysis, not name matching.** A script may declare its own variable called
  `fetch`. What matters is whether a use of `fetch` resolves to the script's own variable
  or to the global. The check uses a scope analyser (`eslint-scope`, the one ESLint uses)
  to tell. A first idea, treating any name declared anywhere in the script as local, was
  wrong: `{ const fetch = 1 } fetch(url)` would have passed. There is a test for exactly
  that.
- **Parsed as it will run.** Scripts are parsed as strict module code with top-level
  `await` and `return`, the form they run in. Parsing them another way would let text mean
  one thing to the check and another to the runtime. No wrapper is added before parsing, so
  a script cannot close a wrapper and continue outside it; that is a syntax error.
- **Fail closed.** If the analysis itself throws, the script is refused.
- **The contract changed: version 1.1.0.** Contract 3 said a script may reference only
  `tools`, `search`, `describe`, `assert` and `console`. Read literally that would refuse
  `JSON`, `Math` and `Promise`, and no useful script could be written. The contract now
  also lists 34 language built-ins, each pure computation. Nothing a 1.0.0 script could
  rely on was removed.

## Evidence

- 57 tests: scripts that must pass, each blocked construct, each kind of global, size,
  syntax, secrets and the result shape.
- **Against the adversarial suite:** with only this check put in front of the defenceless
  stub, 9 of the 40 attacks are now stopped (both host-escape cases, the stray global, the
  four blocked constructs, the oversized script and the secret literal), the other 31 are
  still open as expected, and both controls are still served. So it stops what it is meant
  to and does not block ordinary scripts.

## Limits

- **It reads text; it cannot follow values.** `tools["con" + "structor"]`, or a property
  name fetched from a tool result, passes this check. Only the sandbox stops that: the
  Workers runtime refuses to turn text into code, and a Dynamic Worker given no bindings
  has nothing to reach. Task 1.2.1 has to prove that, on a deployed Worker (task 1.2.8).
  This check is a second layer, and must never be described as the boundary.
- **Secret detection is by shape.** A secret with no recognisable shape (a plain password)
  is not caught. Redaction before logging is task 1.4.3.
- **`Date` and `Math.random` are allowed,** so a script can read the clock and get random
  numbers. That makes runs not exactly repeatable. Accepted for now.
- **Typed arrays, `TextEncoder`, `URL` and `setTimeout` are not allowed.** Default deny
  means a script that needs one is refused until it is added on evidence.
- **Run inside the local Workers runtime, not yet on Cloudflare.** Since task 1.2.4 the
  check runs inside the local runtime as part of the code tool's end-to-end tests. It has
  not run on a deployed Worker.
- **Two runtime dependencies were added:** `acorn` 8.19.0 (the parser) and `eslint-scope`
  9.1.2 (the scope analyser), with three small packages they need. Both are widely used
  and are pinned; they are also new supply-chain surface in the part of the system that
  judges scripts.

## Changed 2026-11-23: an unknown name is an error the model may fix

Decided by the project owner. Until now every name the check did not know was refused as
`static_check_failed`, a security code. Since task 1.7.3 a security code closes the task
with no retry, so a misspelt variable lost the whole request and paused the project.

Now there are two kinds of refusal for a name outside the Sandbox API:

| The name | Refused as | Retry |
|---|---|---|
| Reaches outside in some JavaScript runtime: `fetch`, `process`, `globalThis`, timers, `crypto` and the rest of `REACH_GLOBALS` | `static_check_failed` | No. The task is closed and escalated |
| Anything else unknown: a typo, an undeclared variable, a built-in that is not on the list | `script_error` | Yes, within the retry limit |

**Nothing unknown runs either way.** The allowlist is still what keeps a script in. The
list of reaching names only decides which refusals count as probing.

If a script has both kinds of problem, the refusal is the security one.

Limit: `REACH_GLOBALS` is a list someone wrote, so it can miss a name. A missed name is
still refused; the cost of a miss is that a model gets up to three tries at it within one
request instead of one.
