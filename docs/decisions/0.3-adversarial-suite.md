# 0.3 The adversarial suite

Date: 2026-11-22. Covers tasks 0.3.1 (the cases), 0.3.2 (run in CI against a stub) and
0.3.3 (run on every change). Requirement: FR-31.

## What it is

40 attack cases and 2 control cases in `src/adversarial/cases.ts`. Each attack names the
rows of the signed-off threat table it covers (`docs/decisions/0.1.10-threat-scores.md`)
and the requirements whose control it exercises. Run it with `npm run adversarial`.

A case attacks a **target** and reports whether the attack was stopped. The target is
whatever is under test. Today that is only the stub; from Phase 1 it is the real server.

## Design choices

- **Judge by what happened, not by the error code.** Most cases give the target invented
  tools that count the calls reaching them. The attack counts as stopped only if the
  harmful call never arrived, or the secret never came back. A target cannot pass by
  returning the right error name while still doing the harm.
- **No way to check means not defended.** A target exposes probes (run a script, show the
  typings, accept a token, and so on). If a probe is missing, the case reports the attack
  as open. A target that throws is also reported as open.
- **Controls stop a target passing by refusing everything.** Two ordinary requests (an
  allowed read, and a tool error the script catches) must be served.
- **The stub has no defences, on purpose.** It runs the script in the test process with
  the host in reach and calls every tool it is given. Every attack must be reported open
  against it. If one were reported as defended, that case could not tell a defence from
  its absence, and the run fails. This is the check that the suite itself works.
- **No real secrets, and no secret-shaped text in the repo.** The stand-in token is
  assembled at run time, so the repo's secret scan has nothing to find. A test checks the
  source for token-shaped literals.

## In CI

The `test` job, which every pull request must pass, runs `npm run adversarial` after the
unit tests. The workflow has no path filter, so a change to anything, including the
policy contract, a runtime or dependency pin, or the model list, runs the suite. A test
fails if a path filter or a condition is added to the workflow.

## Limits, stated plainly

- **Passing against the stub proves the suite can detect, not that anything is safe.** No
  defence exists yet. The first real run is against the Phase 1 server before Gate 1,
  where the expectation flips: every attack defended, every control served.
- **Sixteen cases ask the target a question instead of attacking it.** Token checks,
  paused runs, approvals, saved scripts, the audit log, the local listener, console
  sign-in, process reach, the build's pins, the reviewer and forced pauses are reached
  through small probe functions. For the stub these are one-line answers. The Phase 1
  adapter must implement each probe by really attempting the action against the server;
  an adapter that just answers "refused" would make those cases worthless. This is the
  main thing to review when the adapter is written.
- **One case per threat is a floor.** Rows 6, 7, 10, 13, 15, 16, 17 and 19 have a single
  case each. More are added as each control is built, and after any incident.
- **The escape cases are simple.** They cover reading the host environment, the
  constructor chain, a stray network global and the four blocked constructs. They do not
  cover runtime bugs; those are met by patching (FR-23) and the second layer (FR-24).
- **The time-limit case uses real time** (twelve calls of 25 ms against a 60 ms limit). It
  is generous, but a heavily loaded machine could in theory blur it for a real target.
- **Dynamic import is checked in a plain Node process.** The unit-test runner's own
  module loader stops dynamic import in constructed code, which would hide that case, so
  the stub run in the tests is the same command CI runs.

## First run against ExecWard itself, 2026-11-24

Until this date the suite had only ever been run against the stub. That showed the
suite can detect; it showed nothing about ExecWard. Gate 1 asks for the suite passing,
so the real target was built (`src/adversarial/execward-target.ts`) and the suite run
against it.

**What the target is.** The real `code` tool through `codeToolService`, as a served
route must use it: static check, Dynamic Worker executor, broker, policy table, pins,
quotas, switches, audit log, the console's sign-in rule and the escalation queue. Only
the stores are in memory, and the upstream tools are the suite's own counted fixtures.
It runs inside the test Worker, because the sandbox is only real there.

**Result, on Cloudflare** (`npm run adversarial:real`): 40 attacks, 32 defended, 8 on
parts not built yet, none open. Both controls served. Against the stub, unchanged: all
40 open.

| Stopped by | Attacks |
|---|---|
| Static check, before the script ran | 9 |
| Policy (data-flow rule, caller rule, no policy record) | 5 |
| Quotas, the time limit, the circuit breaker | 4 |
| Argument and result checks | 3 |
| Pinned definition changed | 1 |
| Result marked as untrusted | 1 |
| Approval of descriptions, audit log, console sign-in, queue, platform, build | 9 |

**The 8 not built** are attacks on parts Phase 1 does not have, so there is nothing to
attack and nothing to defend. Each names the task that builds the part
(`src/adversarial/expected.ts`): remote sign-in with tokens (2.1.2), the independent
reviewer (2.2.3, two cases), approvals (3.1.5, two), paused runs (3.1.6, two), saved
scripts (4.1.1). A test fails if a listed attack is ever reported as defended, or if
its task is marked Done while it is still on the list.

**It runs three ways.** In `npm test`, in the local Workers runtime, on each commit's
own code. In `npm run test:deployed`, on Cloudflare. And by hand with
`npm run adversarial:real`, which also judges the one case about the build.

**Later the same day,** sign-in for model clients was built (task 2.1.2), so the attack
"a token issued for another service is accepted" came off the not-built list and is now
tried against the real MCP entry point: 33 defended, 7 not built. The test that ties
each open attack to an unfinished task is what forced this: it failed when 2.1.2 was
marked Done.

### What the first attempt got wrong

The first run reported 30 defended and one control refused. The refused control was
the warning: ExecWard refuses any argument a schema does not declare, and the suite's
ordinary fixture tools declared none, so every tool call was being turned away for its
arguments and most attacks looked stopped for the wrong reason. Three changes to the
suite followed, none to ExecWard:

- The ordinary fixture schema now says it accepts any fields.
- The edited-log case edits the line it wrote, not the first line of the log, which in
  a real log may be an earlier entry. This was the one attack that had got through.
- The host-environment cases plant their stand-in secret only where a host environment
  exists. Inside a Worker there is none.

To keep this from recurring, the test checks not only that each script attack was
stopped but by which error code (`STOPPED_BY`).

### Limits of this run

- **The escape cases never reach the sandbox.** The static check refuses all of them
  first. What the sandbox itself withstands is shown by the tests of task 1.2.8.
- **Two answers describe the platform and are not attempts:** that a Worker has no
  local listener, and that it cannot read the files of the computer it runs on.
- **"The source is shown"** in the forced-pause case means the owner is shown the run
  and the tool. The planted text is not copied into the queue.
- **Stores are in memory.** The database stores are tested elsewhere.
- **One run on one day.** CI repeats it on every change.
