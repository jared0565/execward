# 0.3 The adversarial suite

Date: 2026-11-22. Covers tasks 0.3.1 (the cases), 0.3.2 (run in CI against a stub) and
0.3.3 (run on every change). Requirement: FR-31.

## What it is

40 attack cases and 2 control cases in `src/adversarial/cases.ts`. Each attack names the
rows of the signed-off threat table it covers (`docs/decisions/0.1.10-threat-scores.md`)
and the requirements whose control it exercises. Run it with `npm run adversarial`.

A case attacks a **target** and reports whether the attack was stopped. The target is
whatever is under test. Today that is only the stub; from Phase 1 it is the real server.

## Design choices

- **Judge by what happened, not by the error code.** Most cases give the target invented
  tools that count the calls reaching them. The attack counts as stopped only if the
  harmful call never arrived, or the secret never came back. A target cannot pass by
  returning the right error name while still doing the harm.
- **No way to check means not defended.** A target exposes probes (run a script, show the
  typings, accept a token, and so on). If a probe is missing, the case reports the attack
  as open. A target that throws is also reported as open.
- **Controls stop a target passing by refusing everything.** Two ordinary requests (an
  allowed read, and a tool error the script catches) must be served.
- **The stub has no defences, on purpose.** It runs the script in the test process with
  the host in reach and calls every tool it is given. Every attack must be reported open
  against it. If one were reported as defended, that case could not tell a defence from
  its absence, and the run fails. This is the check that the suite itself works.
- **No real secrets, and no secret-shaped text in the repo.** The stand-in token is
  assembled at run time, so the repo's secret scan has nothing to find. A test checks the
  source for token-shaped literals.

## In CI

The `test` job, which every pull request must pass, runs `npm run adversarial` after the
unit tests. The workflow has no path filter, so a change to anything, including the
policy contract, a runtime or dependency pin, or the model list, runs the suite. A test
fails if a path filter or a condition is added to the workflow.

## Limits, stated plainly

- **Passing against the stub proves the suite can detect, not that anything is safe.** No
  defence exists yet. The first real run is against the Phase 1 server before Gate 1,
  where the expectation flips: every attack defended, every control served.
- **Sixteen cases ask the target a question instead of attacking it.** Token checks,
  paused runs, approvals, saved scripts, the audit log, the local listener, console
  sign-in, process reach, the build's pins, the reviewer and forced pauses are reached
  through small probe functions. For the stub these are one-line answers. The Phase 1
  adapter must implement each probe by really attempting the action against the server;
  an adapter that just answers "refused" would make those cases worthless. This is the
  main thing to review when the adapter is written.
- **One case per threat is a floor.** Rows 6, 7, 10, 13, 15, 16, 17 and 19 have a single
  case each. More are added as each control is built, and after any incident.
- **The escape cases are simple.** They cover reading the host environment, the
  constructor chain, a stray network global and the four blocked constructs. They do not
  cover runtime bugs; those are met by patching (FR-23) and the second layer (FR-24).
- **The time-limit case uses real time** (twelve calls of 25 ms against a 60 ms limit). It
  is generous, but a heavily loaded machine could in theory blur it for a real target.
- **Dynamic import is checked in a plain Node process.** The unit-test runner's own
  module loader stops dynamic import in constructed code, which would hide that case, so
  the stub run in the tests is the same command CI runs.
