# 1.9.3 Per-run metrics, and the scheduled housekeeping

Date: 2026-11-23. Requirement: NFR observability; also serves tasks 1.4.4, 1.6.7, 1.6.8
and 1.3.8. Status: **built and tested in memory. Since then the metrics go to
Cloudflare's logs, and the production Worker's timer calls the housekeeping every five
minutes** (docs/decisions/production-schedule.md).

## Metrics (`src/metrics/metrics.ts`)

One record per run, for whatever monitoring is chosen:

| Field | Meaning |
|---|---|
| Status and error code | How the run ended |
| Security event | True when it ended on a security code. Alerts are built on this |
| Duration | Latency of the run inside ExecWard |
| Tool calls, failed calls, records read, retries | From the run report |
| Verification | The release gate's marking |
| Tokens | Script, returned, kept-out and estimated saving. Present only when metering is on, and labelled estimated |

**Numbers and fixed codes only.** No script, argument, result, tool name or error text.
A test fills a run with marked text in every one of those places and checks that none
of it reaches the metric.

Metrics are apart from the audit log and cannot fail a run.

## Housekeeping (`src/maintenance.ts`)

Several tasks ended with "nothing runs it on a schedule". This is the thing a schedule
will run. Two rounds:

- **Every few minutes:** close escalations past their time limit; send the hourly
  reminder for an open security exception.
- **Daily:** apply retention to the audit log; check the reviewer model (added by task
  2.2.4); send the digest; sweep quota counters whose window has ended; remove stats rows
  past 90 days (added by task 2.3.1).

Each job stands alone. One failing does not stop the rest, and the result lists which
ran and what each did, as counts.

## Limits

- **The monitoring stack is Cloudflare's own logs** (Workers Logs), chosen by the
  project owner on 2026-11-24: no new account, credential or outside address. Each run
  writes one line named `execward_run` (`logMetricsSink`). On 2026-11-24 the line was
  seen arriving in the test Worker's live log on Cloudflare, for a completed run and a
  refused one. Workers Logs keeps lines for days, not months; there are no charts. The
  stored copy was not queried, only the live stream. Since Phase 2 production
  writes the line for every run it serves (`src/mcp/production.ts`).
- **The production Worker's timer calls the housekeeping** (`src/worker/scheduled.ts`).
  When this was written nothing called it.
- **Duration is ExecWard's own clock for the run.** It is not the latency a model or a
  user sees, and it is not the overhead figure task 1.9.4 asks for.
- **Alerts are not built.** That is task 3.1.10; these metrics are what it will read.
