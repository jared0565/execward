# 1.2.4 The `code` tool's input and output

Date: 2026-11-22. Requirements: FR-1, FR-5, interface contracts 1 and 2. Status: **built
and tested. Served since task 2.1.2** at the MCP address, behind Cloudflare Access. The
Limits below were brought up to date on 2026-11-27.

## What it does

`runCodeTool(input, deps)` in `src/code-tool/run.ts` is the run path:

1. **Static check** (task 1.2.3) on the script text. A refusal is `static_check_failed`.
2. **Input contract.** Anything that does not match is refused with `schema_invalid`.
3. **Executor** (task 1.2.1) runs the script.
4. **Output contract.** The reply is one of the contract's shapes, checked before it is
   returned. A reply that would not match is replaced by a `sandbox_fault` error.

Every reply carries a run report: run ID, the script's SHA-256, calls per tool, errors and
duration.

## Choices

- **The static check runs before the input check.** An oversized or hostile script is
  always reported as that, even if the rest of the input is also wrong. A security
  finding should not be hidden behind a formatting error.
- **Truncation notice (FR-5).** An oversized final value comes back as
  `{ notice, partial }` with `truncated: true`. The notice tells the model the value was
  cut, that `partial` is not complete JSON, and to return less.
- **Each way a run can fail maps to one error code:** script error, failed assertion,
  timeout, quota and sandbox fault.
- **A refused call still counts** in the report's calls per tool.
- **Contract version 1.2.0: optional `logs`.** The Sandbox API said `console.log` output
  is "captured and returned", but the output contract had no field for it. `logs` is now
  an optional field on completed and error replies. Like the result, it is untrusted.
- **A fault never falls back** (task 1.2.7). If the executor throws, the reply is
  `sandbox_fault` and nothing else runs. A test injects a failing executor and counts zero
  upstream calls.

## Evidence

- 27 tests with a scripted executor: every bad input, the static check in the path, the
  report, the notice, each failure mapping, the injected fault.
- 4 tests end to end inside the local Workers runtime: input, static check, the real
  Dynamic Worker executor, and the output contract together.

## Limits

- **Reached through `src/service.ts`,** which supplies the broker as the host the script
  talks to, and is what the MCP route calls. When this was written there was no route, no
  sign-in and no broker.
- **Report fields that are still placeholders:** records written and side effects are
  always zero or empty, because nothing writes yet. Records read, retries and
  verification are now filled in (tasks 1.3.6, 1.7.3, 1.7.4 and 2.2.3).
- **The result is marked as untrusted for the model** (FR-36), since task 1.3.6: the MCP
  adapter hands every reply over through `presentForModel`.
- **`paused` is returned in one case:** a critical figure that fails the cross-check
  (task 2.2.2). Approvals do not exist yet.
- **The duration includes the static check** and uses the host's clock.

## Added by task 1.2.6: `assert()`

- A failed assertion ends the run. If the script catches the error and carries on, every
  later tool, search and describe call is refused inside the sandbox, and the run is still
  reported as `assertion_failed`. So no side effect can follow a failed assertion.
- The error says what failed: the message, what the condition actually was (for example
  `0` or `null`), the line, and the text of that line.
- Passed assertions are counted in the run report.
- Limit: the cut-off after a failed assertion is kept inside the sandbox, beside the
  script. It is out of the script's reach by ordinary means, but it is not enforced by the
  host. Tier-1 and tier-2 tools must not rely on it alone; the broker decides those.
