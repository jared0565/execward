# 1.5.2 to 1.5.4 Typed functions, discovery and pinned definitions

Date: 2026-11-23. Requirements: FR-2, FR-3, FR-22. Status: **done and tested in memory,
against tool definitions supplied by the tests.** The GitHub connector (task 1.5.1) is not
built, so nothing here has yet met a real tool's definition.

## What a script sees (FR-2)

Each wrapped tool becomes one typed async function. `my-server.list-items` becomes
`tools.my_server_list_items(args)`. Argument and result types come from the tool's
schemas. A tool with no output schema returns the generic type. Any part of a schema the
converter does not understand becomes the generic type too; it never guesses.

## How a model finds tools (FR-3)

The description of the `code` tool that a model is given names no wrapped tool at all. A
test checks this against the GitHub inventory. The model calls `search()` for names and
`describe()` for one tool's types. `describe()` shows the definition that was approved,
not whatever the tool says today.

## Pinning (FR-22)

A tool's description is text a third party wrote and a model reads. Approval pins a
definition by hash. At every call the tool's current definition is compared with its pin:

| What the tool says now | Result |
|---|---|
| Same as the pin | Allowed |
| Only the description changed, and the new one passes the scan and the length cap | Allowed, and noted |
| The schema changed, the tool is gone, it answers under another name, or the new description fails the scan | `definition_changed`; the run ends |
| The policy record names a different pin from the registry | `definition_changed` |

## The description scan

A description is refused at approval, and withheld wherever it would be shown, if it is
longer than 1,000 characters, contains hidden or control characters, or shows a sign of
addressing the reader: telling it to ignore instructions, speaking as the system, giving
orders, asking for data to be sent somewhere, a link, markup, or a mention of credentials.

Descriptions written inside a schema are never shown.

## Choices

- **A clean rewording is let through.** The PRD asks for this. Stopping work every time
  an upstream tidies its wording would train the owner to approve without reading.
- **A schema change always needs the owner.** The schemas decide what a call may send
  and what comes back.
- **Checked at every call, not once per run,** so a change made mid-run is caught.
- **A changed definition ends the run** like any other security refusal.
- **Two tools whose names clean to the same function name are refused at start-up.**

## Evidence

52 tests: the conversion rules, every description in the GitHub inventory passing the
scan, thirteen kinds of bad description flagged, six kinds of changed definition blocked
with nothing forwarded, a mid-run change caught, and the no-catalog check.

## Limits

- **The scan is a list of obvious signs.** It stops crude attacks. A carefully worded
  description that steers a model without tripping a pattern would pass. The pin is the
  real control: the owner reads a description once, and it cannot then change unseen
  except by a rewording that also passes the scan.
- **That exception is the weak point.** A reworded description that passes the scan is
  accepted without the owner. It is noted but not yet written to the audit log, and the
  model is still shown the approved wording, not the new one.
- **The scan will refuse some honest descriptions,** for example one that includes a
  link to documentation. Those tools cannot be approved until the owner console offers
  an override.
- **Pins are held in memory.** A table for them, and the approval action, come with the
  connector and the owner console.
- **Schema conversion covers the common keywords only.** `$ref`, `oneOf` and `allOf`
  become the generic type.
- **The wording of the `code` tool's description is a first draft.** Task 1.9.6 tests it
  with both model families.
