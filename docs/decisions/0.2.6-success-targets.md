# 0.2.6 Success-metric targets and the latency budget

Date: 2026-11-22. Status: decided by the owner, and written into the PRD (revision 185,
"Success metrics" table and the Performance row of the non-functional requirements).

The PRD's targets were all marked "proposed" until the Phase 0 baseline existed. With the
baseline in hand (`docs/research/0.2.5-baseline-report.md`) the owner confirmed or changed
each one.

## Targets the baseline informed

| Metric | Was proposed | Now | Why |
|---|---|---|---|
| Input tokens per task | At least 30% lower on tool-heavy tasks | At least 30% lower than direct calls on bounded tool-heavy tasks, on each model | Tool search alone saves 10% to 13%, so 30% is clear of it. Direct-call comparison points: 39,246 input tokens per tool-heavy run on Claude Haiku 5.5 and 24,013 on GPT-6 Luna. |
| Task success rate | No more than 5 points below direct calls, with the confidence interval | The same, **and** no task that passes with direct calls but fails every run with the code tool | Direct success is 99.3% on both models. With 150 runs per model the suite detects a drop of about 5 points, not less. The added rule exists because an average hides a consistently broken task: under tool search Claude failed one task 5 times out of 5 while its overall drop was 4 points. |
| Latency added by the sandbox, broker and checks | Under 10% of run time | 10% of run time or 0.5 seconds per run, whichever is larger | A direct-call run has a median of 3.0 s (Claude) and 3.8 s (GPT), so 10% alone would be 0.3 s and would fail short runs over overhead nobody would notice. |

These three are what Gate 1 (task 1.9.8) checks: the token saving, the success drop that
counts as significant, and the latency budget (task 1.9.4).

## Targets confirmed as written

The baseline gives no reason to change these, and the owner confirmed all seven.

| Metric | Target |
|---|---|
| Model round trips per task | Lower on tool-heavy tasks; reported, no hard floor. Baseline: 2.0 to 2.1 turns per tool-heavy run with direct calls. |
| Script failure rate | No more than 10% of scripts fail, on each model. Set by the owner on 2026-11-23 from the first measurement (task 1.9.5): 4.4% on Claude Haiku 5.5, 0% on GPT-6 Luna. |
| Ungated side effects | Zero |
| Sandbox escapes or credential exposures | Zero known |
| Human escalations | 5 or fewer per 100 runs after Phase 3 |
| Silent errors | Zero known; each one found adds a check |
| Net token saving | Positive on tool-heavy tasks; if not, narrow the model-backed checks or switch Code Mode off for that task type |

## Cautions

- The run times above come from invented data that answers instantly, so they are almost
  entirely model time. Real runs that call GitHub will be longer, which makes the 10% part
  of the budget easier to meet, not harder.
- The 5-point figure treats runs as independent, which five runs of one task are not. The
  rule against an always-failing task covers the case this misses.
- Tightening the success bar to 3 points would need about 400 runs per model and arm. The
  owner chose not to.
- All of this was measured on two small models. If larger models are added as targets
  later, the comparison points have to be measured for them too (task G.5).
