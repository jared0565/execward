# 1.3.4 Checking a tool's result and tagging it

Date: 2026-11-23. Requirements: FR-35, FR-7. Status: **done and tested in memory.** No
real tool was wrapped when this was written; fifteen GitHub tools are now (task 1.5.1).
Brought up to date on 2026-11-27. The owner confirmed the per-run reading of "tags" on 2026-11-23
(see "Tags").

## What it does

Every result a wrapped tool returns passes through the broker before the script sees it.

| The result | What the script gets |
|---|---|
| Is not valid JSON data | An error, `schema_invalid` |
| Is larger than 1 MB | An error, `result_too_large`, with advice to ask for less |
| Does not match the tool's output schema | An error, `schema_invalid` |
| The tool itself reported an error | An error, `upstream_error`, carrying the tool's message cut to 500 characters. For a tool marked sensitive the message is withheld and only the status code is given |
| Is fine | A copy of the result |

All four errors can be caught by the script, and the run goes on. None is a security
refusal. Repeated errors ending a run is the circuit breaker (task 1.3.8).

## Tags

The task says "every value carries its tags". What is built:

- For each result handed to a script, the broker records the source tool, its data
  class, whether it is sensitive, and its size.
- The run has one data class: **the highest class of anything the script has read.**
  Whatever the script returns or sends on is treated as carrying that class.

Tags are **not** attached to values inside the script. A script can copy one field out of
a result, join two results, or turn text into a number; any tag riding on the value could
be dropped the same way, by accident or on purpose. A tag is only worth having if the
script cannot remove it, so it is kept with the run, in the host.

The cost is precision. A run that read one confidential file and one public licence is
confidential as a whole, even if it returns only the licence name. That errs on the safe
side. If finer tracking is ever wanted it is a larger design, and should be decided then.

## Choices

- **The script gets a copy.** The result is turned into JSON, measured, and read back.
  What was measured is what is delivered.
- **Results are checked more loosely than arguments on one point.** An extra field in a
  result is allowed unless the schema forbids it: an upstream adding a field is normal,
  and refusing it would break tools for no gain. Arguments stay strict.
- **A rejected result is not handed over.** The reason given to the script, and a tool's
  own error message, count as a read of that tool's data class, because they are worked
  out from its data. A sensitive tool's are withheld and not counted. (Changed after the
  sandbox reviews; at first a rejected result was not tagged at all.) Since 2026-11-27
  no such error carries the original as its `cause`, so a script gets the cut text that
  was counted and nothing more.
- **A tool's own error message is untrusted text.** It goes to the script, cut short. It
  is not scanned for injected instructions; every reply is marked untrusted instead
  (task 1.3.6, FR-36).

## Evidence

16 tests: malformed results, the size limit in bytes, the output schema, tool-reported
errors, the tags, and the run's data class in different orders.

## Limits

- **A tool with no output schema has its result checked for size and JSON only.**
- **The data-flow rule (1.3.5) and output masking (1.3.6) act on the tags.** Neither
  existed when this was written.
- **Not exercised in the local Workers runtime.** These checks are plain logic with no
  runtime-specific parts; the earlier whole-stack tests still pass through them.
- **There is no MCP client to turn a real `isError` result into this error.** The GitHub
  connector (task 1.5.1) raises the error itself when GitHub refuses a request.
