# 1.1.2 The GitHub credential, and the first run against GitHub

Date: 2026-11-23. Requirements: NFR secrets; NFR credentials; FR-24. Status: **done for
the test Worker. The production credential is a separate decision, not yet made.**

## What was done

The project owner created a fine-grained GitHub token: one repository, read-only on
Contents, Issues, Pull requests and Metadata, expiring in 30 days. The owner stored it as
the secret `GITHUB_TOKEN` on the test Worker, typing it into Wrangler's own prompt. It
was never in the chat, the repository or a command line.

Then `npm run test:deployed` ran the GitHub connector on Cloudflare, behind the whole
stack: code tool, static check, sandbox, broker, pinned definitions, policy.

| Check | Result |
|---|---|
| A script reads a repository | Works. The reply holds only what the script returned |
| A script combines three reads and returns a summary | Works |
| The credential anywhere in a reply | Absent. Checked inside the Worker, where the credential is known |
| What a script can see of the tools, the docs, a search, an error and its stack | No credential, no header |
| GitHub refuses a missing issue | The script receives "GitHub answered 404" as an error it can catch |
| A tool outside the fifteen | Refused by the broker. Nothing is sent |
| **A write attempted with the credential** | **GitHub answered 403** |

It is the only upstream credential, and it is for one server.

## What the run found

**A script could break its own reply by calling a tool named like a built-in.** Turning
the tools object into text calls tools named `toString` and `valueOf`. The run report
counted calls in an ordinary object, where those names already exist, so the count was
not a number, the reply failed its own contract, and the run ended as a sandbox fault.
The counters now have no built-in names. Three tests cover it, and fail without the fix.

## Limits

- **The test credential expires in 30 days.** After that the five GitHub tests skip, and
  say so. They do not fail.
- **Production has no credential yet.** On 2026-11-24 the owner chose a GitHub App
  that issues hour-long tokens; see the last section. Nothing warns before the test
  token expires.
- **The write test used one endpoint,** creating a file object nothing points to. A 403
  there shows Contents is read-only. It does not test every kind of write.
- **The test secret now also unlocks reads** of whatever the token covers, through the
  test Worker. That is one public repository.
- **Settled the same day: ordinary mistakes that look like tool calls.** `String(tools)`,
  `JSON.stringify(tools)`, `await tools` and `return tools` each made the sandbox call a
  tool named `toString`, `toJSON` or `then`, which ended the run as a policy refusal and
  closed the task. The owner chose to have the tools object ignore names that cannot be
  a tool path. A path is letters, digits and underscores with an underscore inside; any
  other name is now simply absent. A name of the right shape that is not approved still
  reaches the broker and ends the run. The check is in `src/executor/sandbox-modules.ts`.

## Production: a GitHub App (task 2.1.10)

Date: 2026-11-24. **Decision by the project owner:** production reads GitHub through a
private GitHub App, not a long-lived token. Status: the code is built and tested; the
App does not exist yet, and only the owner can create it.

### Why

A fine-grained token lives up to a year, must be rotated by hand, and works for
whoever holds it until it is revoked. With an App, the only thing stored is the App's
private key. ExecWard uses it to sign a statement good for nine minutes, and GitHub
exchanges that for a token good for about an hour, limited to the App's permissions
and the repositories the owner installed it on.

### What is stored, and where

| Thing | Where | Life |
|---|---|---|
| The App's private key | Worker secret `GITHUB_APP_PRIVATE_KEY` | Until the owner replaces it |
| The App's ID and its installation's ID | Worker secrets `GITHUB_APP_ID`, `GITHUB_APP_INSTALLATION_ID` | Not secret in themselves; kept out of every file |
| The installation token | The running Worker's memory only | About an hour; replaced five minutes early |
| The signed statement | Nowhere | Used once |

Nothing of these is written to the database, the audit log or a log line. Any failure
to get a token gives the connector no credential, and nothing of GitHub's reply or the
error is passed on.

### What the owner sets on the App

Private (only the owner's account can install it). No webhook. Repository permissions,
all read-only: Actions, Contents, Issues, Pull requests, Metadata. No account permissions.
(This list first left out Actions, which the tool that lists workflow runs needs. The
owner was given the full list.)
Installed on chosen repositories only.

### Setting production up

Decision by the project owner, 2026-11-24: add the 15 read-only GitHub tools to
production, and one project, `execward`, at the internal level. Runs under it may read
repository details (branches, commits, issue and pull request lists) but not file
contents or code search, which are classed confidential. Internal is also the most a
personal-plan sign-in to Claude Code or Codex is allowed (FR-38), so nothing is lost
by it today.

`npm run setup:github -- --yes --project NAME --class CLASS` does this
(`src/setup/github-setup.ts`). It needs control of the Cloudflare account, writes an
audit entry naming each tool and its definition hash before it changes anything, and
switches nothing on.

### The write check

Decision by the project owner, 2026-11-24: prove the App cannot write by trying, from
production, at the owner's request. The console has a button for it
(`src/connectors/github-write-check.ts`). Signed in as the owner, with a request from
the console's own page, production tries to create one file object that nothing points
to in a named repository and reports GitHub's status. Only 403 counts as refused. The
answer is written to the audit log whatever it is. Nothing of GitHub's reply is kept.

### Limits

- **A refused write has not been seen for the App yet.** The check is built; the owner
  has not run it.
- **If GitHub accepted the write,** an object nothing points to would exist in that
  repository. It is invisible and GitHub removes such objects in time, but it would
  mean the App's permissions are wrong.
- **The one read was of a public repository.** It shows a token was minted and
  accepted: with no token the connector fails, and GitHub rejects a bad one. It does
  not show which repositories the App is installed on.
- **The private key is a real credential,** the first the production Worker holds.
  Whoever has it can read the chosen repositories, and nothing else. If it leaks, the
  owner deletes it on the App's page and makes a new one.
- **The token is kept per running copy of the Worker.** Each copy mints its own, so
  GitHub may be asked more than once an hour. Each asking is one request.
