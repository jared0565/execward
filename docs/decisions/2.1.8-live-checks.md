## The duration figure understates work done by the script

Claude Code noticed that the timed-out run reported `durationMs: 211` although it had
been stopped at 1,000 ms of CPU time. Measured on the test Worker, 2026-11-24:

| Script | Time seen by the caller | `durationMs` reported |
|---|---|---|
| `while (true) {}` | 3,797 ms | 11 |
| A loop of 300 million additions | 541 ms | 11 |
| `return 1;` | 97 ms | 12 |

The figure is the host Worker's clock at the end of the run less its clock at the
start. On Cloudflare a Worker's clock stands still while code computes and moves only
when input or output happens. The sandbox finishing or being stopped did not move it.
A timer moved it part of the way; a database query moved it the whole way after the
timeout, but not after the loop that finished. There is no dependable way to read true
elapsed time inside the Worker, so none is attempted.

What this means:

- **`durationMs` counts time spent waiting on tool calls, not time a script spends
  computing.** For a script that mostly calls tools it is close. For one that mostly
  computes it is far too low.
- **It decides nothing.** The CPU limit is enforced by Cloudflare and the wall-clock
  limit by a timer; neither reads this figure.
- **Cloudflare stopped the 1,000 ms run after about 3.8 seconds of real time.** The CPU
  limit is a limit on processor time, applied with some delay. It is not a promise
  about elapsed time.
- Times in the audit log are read after a database write, and those were right in the
  one case checked (16 and 17 are 3.0 seconds apart). They are the better guide to how
  long a run really took.
