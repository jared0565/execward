# 1.1.3 Pinned dependencies and an SBOM per release

Date: 2026-11-22. Requirement: FR-23. Threat-table row 6 (supply chain), scored Medium
likelihood and High impact, the only threat above Low likelihood with High impact.

## What is enforced

`npm run check:supply-chain` fails, in CI on every change and again in the release
workflow, when any of these is not true:

| Rule | Why |
|---|---|
| Every dependency in `package.json` is one exact version (no `^`, `~`, ranges, tags, git or file links) | A range lets a new upstream release in without a change in this repo |
| `package-lock.json` exists, is in step with `package.json`, and gives every package a sha512 content hash and an npm-registry download location | The hash is what stops a changed package under an unchanged version number |
| Every GitHub Actions `uses:` is pinned to a full commit hash | A tag such as `v7` can be moved to other code by whoever controls the action |
| With `--sbom`: the SBOM is CycloneDX, describes this package at this version, and lists every direct dependency at its pinned version | An SBOM that does not match the build is worse than none |

The rules are in `src/supply-chain/pins.ts`, with a test for each way of failing.

## The SBOM

`npm run sbom` writes `sbom.cdx.json` (CycloneDX 1.5, from npm's own `npm sbom`, 143
components today, development tools included). It is built and checked in CI on every
change, so a broken SBOM step is found before a release, not during one. The file is not
committed.

## Releases

A release is a version tag pushed to the repository (`v0.1.0`). `.github/workflows/release.yml`
then installs with `npm ci` (which fails without a lockfile), runs every check, confirms
the tag matches the version in `package.json`, builds and checks the SBOM, and creates the
GitHub release with the SBOM attached.

## Limits

- **The release workflow has not run.** No tag has been pushed. Its checks are the same
  steps CI runs, so those are proven; the last step, creating the release with the SBOM
  attached, is first exercised by the first release (task 1.1.5).
- **Pinned is not the same as safe.** A pin stops a silent change. It does not show that
  the pinned version is free of known flaws; that is the weekly advisory check, task 1.1.4.
- **Pinned actions do not update themselves.** Someone has to move the hash when an action
  is patched. Task 1.1.4 is where that check belongs.
- **The lockfile check trusts npm's format.** It reads `package-lock.json` version 2 or later
  (the file is version 3). It
  does not re-download packages to verify the hashes; `npm ci` does that on install.
- **No container images exist yet,** so there is nothing to pin by digest. The Worker's
  compatibility date and bindings are pinned in task 1.1.1.
