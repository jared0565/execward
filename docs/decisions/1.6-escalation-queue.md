# 1.6.6 to 1.6.9 The escalation queue, its options, time limits and emails

Date: 2026-11-23. Requirements: FR-44, FR-46, FR-49, flag 11. Status: **the logic is
built and tested in memory. Nothing sends mail, nothing runs on a schedule, and the
queue is not stored.** All four tasks stay in progress for those reasons.

## What reaches the queue

A task the code tool closes (task 1.7.3) is raised as one of the PRD's triggers:

| How the task closed | Trigger | Safe action, taken at once |
|---|---|---|
| A security failure | Security exception | The project is paused |
| A tool's definition changed | Tool definition changed | The tool is blocked, when the item names it |
| Retries used up, or a failure a retry cannot fix | Repeated failure | The run is already stopped |

**The pause lands before the reply.** The run waits for the queue before handing its
reply back, so a second run cannot slip in between a refusal and the pause it causes.
The first version raised the item in the background; a test showed the gap, and it was
closed.

The other three triggers in the menu (tier-2 action, cross-check disagreement, unusual
values) are defined but nothing raises them until Phases 2 and 3.

## Options

Each item carries up to four options from a fixed menu for its trigger, ranked safest
first, each saying what it does and whether it can be undone. One is recommended, by a
rule that is shown. The menu and rules are the PRD's table, held as data.

- **The server builds the options.** An answer that is not one of the item's options is
  refused. A model has no way to add one.
- **A false positive is never recommended** and needs a written reason.
- **"Keep paused" leaves the item open.** It records that the owner has looked.
- **The queue applies what it can and says what it cannot.** It can pause and resume a
  project and block and unblock a tool. Revoking a credential, removing a server and
  approving a new definition are the owner's own steps; the option's text says so.

## Time limits

From the PRD's table. An item nobody answers by its limit is closed as expired, in the
safe state it was already in. A security exception and a changed definition never
expire. Nothing is ever approved by expiry.

## Repeated choices

The same choice made three times for the same trigger (and tool, where there is one) is
listed as a proposed rule. **Listing is all that happens.** There is no code that adopts
a proposal, so one cannot be adopted on its own or at all. Security exceptions are never
turned into proposals.

## Emails

An email is fixed text and one link. No project, tool, error text or figure. A test
builds an item full of things that must not leak and scans both emails for each of them.
The link's ID must be random letters and digits, and the link must be https.

Urgent items are sent at once, one email each. The rest wait for one daily digest. An
open security exception is sent again every hour until reviewed.

## Limits

- **Nothing sends mail.** The mailer is an interface. The owner chose on 2026-11-24 to
  send from a subdomain of execward.com with Cloudflare's email sending, so the
  domain's existing mail is not affected. Not built yet.
- **Expiry runs** every five minutes on the production Worker. **The digest and
  reminders do not run,** because nothing sends mail.
- **The queue is kept in the database** and has its page in the owner console (added
  2026-11-24). The record of when each reminder went out is still held in memory.
- **The page shows an item's kind, project, tool, error code, options and
  recommendation.** It does not show the run's report or the error's own words, which
  can hold a client's data. Those stay in the audit log, which has no page yet.
- **Nothing raises an item in production yet,** because the `code` tool is not served
  there. The queue page has only been exercised in tests.
- **The security item does not usually name the tool,** because the refusal that closed
  the task does not carry it in a form the queue can trust. "Block the tool" is then
  refused with a message saying so.
- **A recommendation is only as good as the facts it is given.** With no facts it gives
  the cautious answer. Nothing fills in the kind of task or whether a diff was
  wording-only yet.
- **The 15-minute life of an approval** is a constant with nothing to apply it to until
  tier-2 actions exist (Phase 3).
- **An item's ID is in a link sent by email.** It must come from a random source; the
  store that creates real IDs must use one.
