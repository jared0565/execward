# Task 2.2.1: verification's own credential, provider rule and budget

Decided and built 2026-11-25. Requirement: FR-51.

## What it is for

ExecWard's own checks need to call a model: the cross-check of critical figures
(FR-43, task 2.2.2), the independent reviewer (FR-48, task 2.2.3) and the daily golden
tasks (FR-45, task 2.2.4). Until now the core called no model at all. This task builds
the one way those checks may call one, `src/verify/model-access.ts`, and nothing that
uses it yet.

## The owner's decisions, 2026-11-25

| Question | Answer |
|---|---|
| Which provider gets a dedicated key | OpenAI only. The owner works in Claude, and the reviewer must be a different model family (FR-48). Anthropic can be added later |
| Budget on production | $1 a day and $10 a month |

## What is fixed in the code

- **A credential of its own.** A Worker secret named `VERIFY_OPENAI_API_KEY`, on the
  secret allowlist. It is a key made for this and used for nothing else: not the keys
  the eval scripts use on the owner's computer, and not the GitHub App. It is read when
  a request is sent, and is never in a reply, a usage record or an error.
- **A reach of its own.** Requests go to `api.openai.com` only, through the same guarded
  fetch as everything else but with a separate host list. The GitHub connector's fetch
  cannot call the model provider, and verification's cannot call GitHub.
- **The provider rule (FR-38).** The caller states the highest data class in what it
  sends. The route is "OpenAI API, business account", approved for confidential data.
  Client personal data is refused until gate G.7 is cleared, as everywhere else.
- **The budget (FR-27).** One pair of caps for the whole installation, counted apart
  from the platform's spend caps. Before a request is sent, the most it could cost is
  set aside: its size in bytes as an upper bound on input tokens, plus its full output
  limit. If that does not fit under both caps, nothing is sent. After the reply, the
  amount set aside is replaced with what the provider says was used.
- **Separate metering.** Every call writes its own usage record: purpose, project, run,
  model, input and output tokens as the provider counted them, and the cost. The token
  meter's records are estimates of what the working model saved; these are measured
  counts of what verification spent. They never share a record, so task 2.2.5 can
  subtract one from the other.
- **Nothing kept at the provider between requests.** Each request is sent with
  `store: false`.

## Fails closed

Nothing is sent when: the model has no price in the table, the data is above the
provider's ceiling, there is no key, the request is too large, the budget would be
passed, or the counter cannot be read.

When a request was sent and failed, the amount set aside stays counted. That can
understate what is left of the budget; it cannot overstate it. A side effect is that a
broken key stops calls within a day's budget instead of being retried without end.

## Not done here, and why

- **No model is approved.** The table of models and prices is empty, so production can
  make no call. A model is chosen in tasks 2.2.2 and 2.2.3 on measured figures, and its
  price is read from the provider's price page then, not from memory.
- **Not connected to the Worker.** Nothing calls this module in production yet. The
  first caller (task 2.2.2) connects it, with the database-backed counter and a log
  sink for the usage records.
- **No key exists yet.** The owner creates it when the first live check is due. Nothing
  has been spent.
- **Not seen against the real provider.** Every test uses a fake. The request and reply
  shapes follow the ones the eval's OpenAI client already uses
  (`src/eval/providers/openai.ts`). A first real call needs the key, an approved model
  and the owner's go-ahead for the spend.
- **The cost is counted at the table's price.** Discounts for cached input are ignored,
  so the count can be higher than the bill, never lower, as long as the table's prices
  are current. A price change at the provider needs the table updated.
- **The business-terms route is assumed, not proven.** The code cannot tell what terms
  a key's account is under. The owner should make the key in an account held under
  OpenAI's business terms (docs/research/0.1.6-provider-data-terms.md).
