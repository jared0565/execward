# 1.3.5 The data-flow rule

Date: 2026-11-23. Requirement: FR-29, and the owner's answer that the destination
allowlist starts empty. Builds on the per-run tags of task 1.3.4, which the owner
confirmed on 2026-11-23. Status: **done and tested in memory.**

## The rule

Some tools can send data out of the project: a web search, an email, a public post. The
policy record marks these as **outbound**. Some tools read data that must not leave: the
record marks these as **sensitive**.

| Situation | What happens |
|---|---|
| Outbound call, nothing sensitive read so far | Goes out |
| Outbound call after a sensitive read | Refused; the run ends |
| The same, but the owner has listed destinations for that tool and the call names one | Goes out |
| Outbound call with unusually large arguments (over 16 KB) | Refused; the run ends |
| Any other call with unusually large arguments | Goes out, and is flagged for the audit log |

Every destination list starts empty, so today the third row never applies: after a
sensitive read, no outbound call goes out.

## Choices

- **The rule looks at what the run has read, not at what the call contains.** After a
  sensitive read, an outbound call is refused even if its arguments look harmless. A
  script can encode, split or reword data; inspecting the arguments would only catch the
  clumsy cases.
- **Order matters.** An outbound call before any sensitive read is fine. The same call
  afterwards is refused.
- **A read that failed does not count.** The script never received the data.
- **"Escalates" is a refusal for now.** FR-29 says the call escalates. Approvals do not
  exist yet, so the run ends with `policy_denied`. When approvals are built this becomes
  a pause for the owner's decision.
- **Large arguments to an outbound tool are refused outright,** sensitive read or not.
  Sixteen kilobytes sent to a search box is what carrying data out looks like.
- **The refusal names the tool that was read, never the data.**

## Evidence

12 tests: both orders, a failed read, listed and unlisted destinations, and large
arguments at, over and under the limit.

## Limits

- **A listed destination is trusted with everything.** Once the owner lists a host for a
  tool, a run that has read sensitive data may send to it, and the rule does not look at
  what is sent. Listing a destination is therefore a real decision, and should be an
  audited one (task 1.4.x).
- **A destination is only recognised as a URL the tool's schema marks.** An email address
  or a channel name is not a destination to this rule, so a tool that sends to those is
  always refused after a sensitive read, whatever is listed.
- **Only tools marked outbound are covered.** Data can also leave through a tool that is
  wrongly classified, or through the arguments of a read tool (a search query, for
  example). Getting the classification right is part of approving each tool.
- **The final value returned to the model is not covered here.** That is output hygiene
  (task 1.3.6) and provider rules (task 1.3.7).
- **Flags are kept in memory for the run.** Writing them to the audit log is task 1.4.1.
- **Not exercised in the local Workers runtime;** it is plain logic in the broker.
