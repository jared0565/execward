# 0.2.7 Which task types the code tool is built for

Date: 2026-11-22. Status: decided by the owner.

## Decision

Build the code tool first for **bounded, list-heavy tasks**: work whose route is clear and
whose cost is in reading lists, such as counting, summing or finding the most across pages
of issues, pull requests, commits or CI runs, in one repository or several.

Keep **direct tool calls** for lookups and exploratory work: reading one file, one issue
or one release, and tasks where the model first has to find out where to look.

This is the routing the PRD already proposed for the risk "quality drops on exploratory
tasks". The baseline now supports it with measurements.

## Evidence

From `docs/research/0.2.5-baseline-report.md` (600 real runs on Claude Haiku 5.5 and
GPT-6 Luna, direct arm unless said otherwise):

| Finding | Figure |
|---|---|
| Input tokens per run, bounded tool-heavy against exploratory | 2.4 times (Claude), 2.8 times (GPT) |
| Share of Claude's input tokens used by the eight most expensive tasks, all list-heavy | 54% |
| Input tokens for a list-heavy task | 40,000 to 84,000 (Claude), 23,000 to 53,000 (GPT) |
| Input tokens for the cheapest lookup | about 9,000 (Claude), 6,000 (GPT) |
| Saving from deferring tool definitions (tool search) | 10% (Claude), 13% (GPT) |
| Success with direct calls | 99.3% on both models |

So for these tasks the tokens are in tool results, not in tool definitions. Tool search
does not touch tool results. A script that pages through a list and returns one number
does.

Where tool results dominate, by task type:

- **Bounded tool-heavy, list-style**: tool results dominate strongly. Every one of the
  eight most expensive tasks is of this kind.
- **Bounded tool-heavy, single-call** (one filtered list, one pull request): moderate.
  10,000 to 25,000 tokens on Claude. Some saving is possible; not the first target.
- **Exploratory**: tool results are small (mean 16,500 tokens on Claude, 8,700 on GPT),
  and the one clear failure in the baseline was an exploratory task under tool search.
  Little to save and more to lose.

## What this does not settle

- Nothing here measures the code tool. Whether it keeps success at 99% while cutting
  tokens is what task 1.9.5 measures, against this baseline.
- The suite is near 100% success, so it can show a drop but not an improvement, and it
  has no task that needs many dependent steps. Harder tasks may be worth adding before
  1.9.5. The owner chose not to wait for them before making this decision.
- Two cheap models and 15 tools. With many more tools, definitions would weigh more and
  tool search would save more than it did here.
